# CLAUDE.md — ぐんぐん農園（GUNGUN FARM）

待ち時間を極限まで詰めた農園ゲーム。**ビルド不要・実行時依存ゼロ**の単体Webアプリ。
`index.html` をブラウザで開けばそのまま動く。

## 構成

```
index.html          マークアップ。<script> の並び順が依存関係そのもの
css/style.css       テーマ・1画面レイアウト・アニメーション
js/data.js          作物・加工機・品物の定義（純データ。他に依存しない）
js/engine.js        ルールと進行（純ロジック。data に依存）。時間は外から渡す
js/storage.js       localStorage 永続化（設定・記録・農園そのもの）
js/audio.js         Web Audio API による効果音の合成
js/render.js        DOM 描画。data/engine に依存
js/main.js          進行役とUIバインド。上記すべてに依存
tests/              テスト（lint / ロジック / E2E / シミュレーション / 通しプレイ）
```

## 開発コマンド

```bash
npm ci && npm test   # lint → ロジック → E2E
npm start            # http://127.0.0.1:8082/
npm run simulate     # 育ちの速さと詰みの有無を測る（ブラウザ不要・数秒）
npm run playtest     # 実ブラウザで画面のボタンだけを押して回す
```

CI はリポジトリ直下の `.github/workflows/ci.yml`。ゲーム一覧は
`.github/scripts/discover-games.mjs` が数え上げるので、**ワークフローにゲーム名を書かない**。
**サブディレクトリ配下の `.github/workflows/` は GitHub では実行されない**
（実際に `gomoku-narabe/.github/workflows/ci.yml` が死んだまま残っていた）。

## このゲームの約束

**どんなに長くても10秒。** 作物は最長9秒、加工品は最長10秒。
これが存在理由なので、`tests/lint.mjs` と `tests/logic/growth.test.mjs` の
両方で機械的に見張っている。「1つだけ特別に長いもの」を作らない。

**そして、遊ぶ側を待たせない。** 上限を10秒にしても、畑が一斉に実って一斉に空けば
「全部タップ → 数秒なにもできない」の繰り返しになる。測ったら**1秒以上の待ちが
全体の8.1%**、最長3.5秒あった。**時間差まき**（下記）でこれを 0.1% / 1.3秒 にした。
`npm run simulate` が毎回この数字を出し、**3秒を超えたら失敗する**。

**1画面に収める。** ページはスクロールしない（`body { overflow: hidden }`）。
畑は常に上に見えていて、下の段だけがタブで入れ替わる。
`tests/e2e/layout.spec.mjs` が 320x568 から 1280x800 までで
「はみ出さないこと」「押せるものが44x44px以上あること」を検査する。

## 壊してはいけない設計上の制約

1. **実行時の依存パッケージをゼロに保つ。** ビルド工程を持ち込まない。
2. **ESモジュールを使わない。** `file://` で直接開いた時に CORS で失敗するため、
   各ファイルは即時関数で `window.GF` 名前空間に公開するクラシックスクリプトにする。
   したがって **`index.html` の script の順序が依存関係**（`npm run lint` が検査する）。
3. **engine の中で `Date.now()` を呼ばない。** 時間は必ず `tick(state, now)` で外から渡す。
   これがあるから、10分の農園経営をロジックテストで一瞬で回せる。
   `readyAt` / `expiresAt` はすべて**ゲーム内時刻の絶対値**で持つ（残り時間で持たない）。
   保存して読み直しても残り時間が変わらないのはこのため。
4. **乱数を直接呼ばない。** `Engine.setRandom()` を通す（`?seed=` の再現とテストのため）。
5. **設定キーは必ず `Store.DEFAULTS.settings` に定義する。** 定義漏れのキーは
   `merge()` で捨てられ、保存しても復元されない。
6. **`localStorage` は必ず try/catch で包む。** 読み書きの両方が例外を投げうる。
7. **`[hidden] { display: none !important; }` を消さない。**
   `display` を持つクラスが既定の `[hidden]` に勝ってしまう。
8. **ルール判断は engine に集約する。** UI は `canPlant` / `canQueue` / `canDeliver` /
   `boatLoadable` を見る。**UI側で条件を書き直すと必ずずれる。**
   ふなびんで実際にやらかした: ボタンの出し分けは「倉庫に在庫があるか」で書き、
   実際に積む処理は「注文のぶんを引いた余り」を見ていた。
   **押せるのに何も積めないボタン**になり、通しプレイが捕まえた（積んだ数 0）。
9. **倉庫に入らなかったものを消さない。** `store()` は「入った数」を返す。
   収穫も取り出しも、入らなければ**畑や機械の中に残す**（消えると理不尽になる）。
10. **収穫と植え直しを別々の操作に戻さない。** 待ちのあるゲームでは
   「収穫する → 何を植えるか決める」が意味のある間になるが、**このゲームには待ちが無いので
   ただの往復**になる。実際に測ったら、その2つだけで全操作の71%を占め、判断のある操作は
   11.5%しか残っていなかった（`ROADMAP.md` に経緯）。`harvest(state, i, replant)` が
   収穫と植え直しをまとめて行う。
11. **時間差まき（`Engine.sow`）を外さない。** まとめて k マス植えるとき、
   j 番目が `sec * (j+1)/k` で実るようにずらしている。畑が順番に実り続けるので、
   いつ見ても収穫できるものがある——**これが「待ち時間を限りなく0に」の中身**。
   - **どの畑も作物の秒数より長くは待たせない**（いちばん遅い1マスがちょうど `sec`）。
     上限が伸びないので10秒の約束は保たれる
   - 1マスだけ植えたときはずらさない（比べる相手がいない）
   - **`harvestAll` は「先に収穫だけ済ませてから、空いたマスをまとめてまき直す」。**
     収穫のたびに1マスずつ植え直すと全部が同じ時刻に揃ってしまう
   - 畑の回転が上がるので、**触ったら経験値カーブを測り直す**（`data.js` の `xpFor` に履歴）
   - **副産物: まとめて収穫するほど次が早い。** k マスまとめて蒔くと平均 `sec*(k+1)/(2k)`
     で実るので、12マスなら約0.54倍、1マスずつなら1.0倍。おかげで**連打が損になる**
     （実測: 200ms間隔は800ms間隔の74%しか稼げない）。
     この性質は狙って作ったものではないが、**遊びを我慢比べにしないために守る**。
     `tests/logic/economy.test.mjs` が「連打がいちばん得になっていないこと」を見ている
12. **どのレベルにも解放されるものを用意する。** 一度、**Lv14〜20 の7レベル連続で
   何も解放されない**状態になっていた（進行の後半3分の1が空っぽ）。
   「レベルに沿って施設と作物が増えていく」がこのゲームの背骨なので、
   `tests/lint.mjs` が「2レベル以上つづけて空」を弾く。
   作物や施設を足すときは `Data.unlockedAt()` に出ることを確かめる。
13. **ふなびんは「余りの行き先」。深い加工品を大量に頼ませない。**
   ふつうの注文とは逆に**安い品へ寄せる**（`makeBoat` の抽選）。
   最初に高い品へ寄せたら ケーキ×11 のような船が出て、**10分で一度も出港しなかった**。
   積む量に合わせて期限も伸ばす（量だけ増やすと、ただの無理難題になる）。
14. **まとめ操作は、注文が欲しがっているものに手を出さない。** `workAll()` と
   開いている注文のぶんを残して仕込む。1タップのボタンが、届けるはずだった品を
   勝手に材料にしてしまうと、押すのが怖いボタンになる。
   `loadBoatAll()` は開いている注文のぶんを残す。1タップのボタンが、届けるはずだった品を
   勝手に使ってしまうと、押すのが怖いボタンになる。
   1台ずつ・1種類ずつ押したときは遠慮しない（そちらは自分で決めた操作なので）。

## 描画の作り方（ここを間違えると操作が効かなくなる）

毎フレーム全部を作り直すと、押した瞬間のへこみもスクロール位置も消える。
そこで「**形が変わったときだけ作り直し、伸び縮みするところだけ毎フレーム塗る**」。
形の変化は署名（sig）の文字列比較で見ている。

**署名にコインの数をそのまま入れてはいけない。**
収穫のたびに数字が変わるので毎フレーム DOM が作り直され、
**押そうとしたカードが指の下で差し替わる**。
通しプレイで「こうぼうのカードを押しても一度も仕込めない」状態を捕まえた。
署名に入れてよいのは**見た目が変わる条件**だけ（買えるか／出せるか、の真偽）。

## ゲーム設計上、動かすと壊れるもの

- **注文は「いま自力で用意できるもの」しか頼まない**（`Engine.obtainable`）。
  持っていない機械の品を頼むと、3枠が埋まったまま進まなくなる。
- **注文はことわれる**（✕）。捨てられないと、同じ理由で詰む。
- **行き止まりの救済（`rescue`）を外さない。** タネも買えず・倉庫は空・畑も機械も
  止まっている状態は自力で抜けられない。**倉庫に何か残っているうちは発動しない**
  （売れば抜けられるので、救済すると経済が壊れる）。
- **倉庫がいっぱいのときは収穫できない。** これが「売る・広げる」を考える理由になっている。
  自動で売る仕組みを入れると、資源管理が消えて畑を眺めるだけのゲームになる。
- **加工品は材料の合計より高くする**（`tests/lint.mjs` が検査）。
  逆だと加工する意味が消える。
- **タネ選びを「偽の選択」に戻さない。** 一度、1秒あたりの儲けも1枠の値打ちも
  **両方とも格上が勝つ**表になっていて、解放された中で格上を選べば常に正解だった
  （タネの一覧はただの飾り）。いまは
  **短いほど1秒あたりが良く、長いほど1枠の値打ちが高い**。
  同じ秒数の作物は、タネ代と売値に**同じ額**を足して差をつける
  （儲けは変わらず、倉庫の持ちだけ良くなる = 上位作物のごほうび）。
  `tests/lint.mjs` が単調性を、`tests/logic/economy.test.mjs` が
  「短いのだけ／長いのだけで回して、どちらかが全部で勝たないこと」を確かめている。
- **機械を買った時点で材料が手に入ること**（解放レベルの前後関係）。
  店に並んでいるのに動かせない機械ができる。lint とロジックテストの両方で見ている。
- **後半の施設ほど、前半で作った品を材料にする。** 作物を並べ替えただけの
  「格上のこむぎ」を足しても増えた気がしない。鎖を伸ばす
  （ピザ = こむぎこ + チーズ + ケチャップ、の4段）。`tests/logic/machines.test.mjs` が
  「後半の鎖が前半より深いこと」を見ている。
- **こうぼうの一覧を並べ替えない。** 出来上がった機械を上に持ってきたくなるが、
  署名（sig）で作り直す作りなので、**仕上がった瞬間に指の下でカードが動く**。
  目立たせるのは色と数字（緑＋バッジ）でやる。

## 手応えの作り方（いちばん繰り返す操作に厚く）

収穫は数千回繰り返す操作なので、ここの手応えがそのまま遊びの質になる。

- **続けて鳴らすほど音が上がる**（`Audio` の `ladder()`）。半音ずつ、8段まで。
  途切れると戻る。同じ音が続くより、段を上がるほうが気持ちよさが出る
- **穫ったものが倉庫の表示めがけて飛ぶ**（`Render.float(..., toBarn)`）。
  まっすぐ上に消えるより「仕舞われた」感じになる。受け取った側も弾ませる（`barnPulse`）
- **粒の数は最大5つ**。12個穫れても5粒。それ以上は散らかって読めなくなる
- **音声ファイルは持ち込まない。** すべて Web Audio で合成する（配信物を増やさない）

## 手を動かす間隔について

**連打がいちばん得になっていないこと**を測る。間隔だけを変えて成果を比べる。

| 間隔 | 10分の稼ぎ | 手数 | 最速の人と比べて |
| --- | ---: | ---: | ---: |
| 200ms | 56,843 | 2,239 | 100% |
| 400ms | 69,783 | 1,425 | 123% |
| **800ms** | **76,387** | **746** | **134%** |
| 1500ms | 62,686 | 400 | 110% |
| 3000ms | 37,546 | 200 | 66% |

ちょうどよいのは**毎秒1回くらい**で、400〜1500ms のどこでも110〜134%。
**幅が広いので狙って合わせる必要がない**——ここが狭いと、遊びが作業になる。
極端に放っておくと落ちる（そうでないと手を動かす意味が無い）。

## 待ち時間の測り方

このゲームの売りなので、機械で見張っている。`npm run simulate` が毎回出す。

- **手持ち無沙汰の割合** … 収穫・植える・取り出す・仕込む・届ける の**どれも無い**時間。
  売り買いは家事でいつでもできるので、待ちの解消には数えない
- **1秒以上つづいた待ちの割合** ← **人が「待った」と感じるのはここ**。
  200ミリ秒の隙間は待ちではない。全体の割合だけ見ると判断を誤る
- **いちばん長く待たされた時間** … 3秒を超えたら `simulate` が失敗する

**採る間隔に注意。** 手を動かす間隔（400ms）と同じ粒度で測ると、
200msの隙間が丸ごと見えず実際より良い数字が出る。100msきざみで採る。

## 面白さの測り方（バランスとは別に要る）

「詰まらない」「ちょうどよく育つ」を測っても、**面白いかどうかは測れていない**。
このゲームで効いた指標は **操作の内訳** だった。

プレイヤーの操作を種類ごとに数え、**判断のある操作（配達・売買・注文を断る・タネを替える）が
全体の何割か**を見る。改修前は 11.5%、収穫と植え直しを1タップにまとめて 24.9% になった。
**8割が無思考の操作なら、それは作業であってゲームではない。**

数え方は `ROADMAP.md` の「測ったこと」にある。触ったら測り直す。

## バランスの測り方

**数値は当て推量で決めない。** `npm run simulate` で実際の秒数ぶん回して測る。
CI の「バランス計測」ジョブが毎回この表を実行の要約に出している。

- 最初の経験値カーブ（`12*level^1.35`）では、手を止めずに回すと**6分でレベル20**に着いた。
  獲得ペースの実測から逆算して `42*level^1.35` に直し、狙い（レベル20 ≒ 17分）に合わせた。
- **閾値は実測より下に置く。** 実測がレベル14なら、テストの閾値は11。
- **シードは `mixSeed()` で撹拌する。** 等差のシードは乱数列どうしが相関する。

### 通しプレイの倍率について

`--speed` を上げすぎると**測るものが変わる**。1手ぶんの操作は Playwright の往復で
300〜600ms かかるので、倍率10では「1手のあいだに農園が5秒進む」ことになり、
人が遊んだときの挙動から離れる（倍率10では5分で加工が3件しか進まず、
詰まりの判定が当てにならなかった）。既定の3倍を大きく超えない。

## テストの構成

| 種別 | 場所 | 実行 | 内容 |
| --- | --- | --- | --- |
| 静的検査 | `tests/lint.mjs` | 依存不要 | 構文・参照・読み込み順・データの整合（**10秒の上限**を含む） |
| ロジック | `tests/logic/*.test.mjs` | `node --test` | 育ち・加工・注文・経済・永続化 |
| ブラウザ | `tests/e2e/*.spec.mjs` | Playwright | 操作ひととおりと、1画面レイアウト |
| シミュレーション | `tests/simulate.mjs` | `npm run simulate` | 育ちの速さ・詰みの有無（ブラウザ不要） |
| 通しプレイ | `tests/playtest.mjs` | `npm run playtest` | 実ブラウザで画面のボタンだけを押して回す |

E2Eは `desktop`（マウス）と `mobile`（Pixel 5 / `hasTouch`）の2プロジェクトで走る。
端末差のある操作は `tests/e2e/fixtures.mjs` の `tap()` に閉じ込め、スペック本体に分岐を書かない。

**ブラウザを取得できない環境では `PW_CHROMIUM` に実行ファイルのパスを渡す。**
`npx playwright install` は使えない（取得が拒否される）。

```bash
export PW_CHROMIUM=$(find /opt/pw-browsers -maxdepth 4 -type f -name chrome | head -1)
npm run test:e2e && npm run playtest
```

## 通しプレイで実際に見つけた問題

- **在庫を抱えたまま破産する。** コインが尽き、倉庫は品物でいっぱい、という状態で手が止まった。
  自力で抜けられる（売ればいい）のに気づきにくいので、タネ代が足りないときは
  みせの「うる」へ案内するようにした。
- **こうぼうのカードが押せない。** 上の「描画の作り方」を参照。
- **仕込み中の機械が薄く（使えないように）見えていた。** 薄くするのは
  「材料も無く、中身も空」のときだけにした。

## 過去の失敗と、繰り返さないためのルール

- **テストに値段や秒数を直書きしない。** 価格表を組み直したとき、
  ロジック3件とE2E4件が「こむぎは1コイン」「初期コインは30」を直書きしていて落ちた。
  **数字はデータから採る**（`Data.crop('wheat').cost` / `Engine.create({}).coins`）。
  テストが確かめたいのは「払った分だけ減ること」であって、その額ではない。
- **テスト結果は `0 failed` を明示的に確認する。** passed の件数だけを見て判断しない。
- **手で確認したことはテストとして残す。** 「一度動いた」より「壊れたら気づける」を優先する。
- **書き捨てのスクリプトをゲームのディレクトリに置かない。** 一度、配信物に混ざりかけた
  （`build-site.mjs` が `.mjs` を落とすようにして塞いだ）。
