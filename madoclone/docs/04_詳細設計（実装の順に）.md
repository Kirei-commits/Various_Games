## 1. 全体の約束

### 1.1 ビルド条件

- `Assets/Game/Data` と `Assets/Game/Core` は、**netstandard2.1・C# 9** で書く（`tools/Mado.CoreLib` がそれで固定している。警告はエラー）。Unity 6 でも dotnet でも同じソースがコンパイルできること。
- `init` アクセサや `record` を使うなら、`System.Runtime.CompilerServices.IsExternalInit` が netstandard2.1 には無いので、**Data アセンブリに空の内部クラスとして1つ定義する**（`namespace System.Runtime.CompilerServices { internal static class IsExternalInit { } }`）。使わずに済ませるなら、読み込み専用フィールドとコンストラクタで書く。
- Data と Core に `UnityEngine` を入れない。`System.Random`・`DateTime.Now` も使わない（`tools/bootstrap/check_sources.py` が検査する）。
- JSON は Newtonsoft.Json。Unity では公式パッケージ `com.unity.nuget.newtonsoft-json`、dotnet では NuGet。Data の asmdef に `overrideReferences: true`・`precompiledReferences: ["Newtonsoft.Json.dll"]` を足す（Unity 側のアセンブリ名は実際に開いて確かめる）。
- 名前空間はフォルダと揃える：`Mado.Data`、`Mado.Core.Util`、`Mado.Core.Wallet`、`Mado.Core.Save`、`Mado.Core.Growth`、`Mado.Core.Stats`、`Mado.Core.Battle`。向きの規則は `check_sources.py` に入っている。
- 識別子は ASCII、コメントとドキュメントは日本語。

### 1.3 エラーの扱い（3種類を混ぜない）

| 種類 | 例 | 扱い |
|---|---|---|
| データの誤り | JSON に未知の項目、存在しない ID、長さ3でない配列 | 読み込み時に `DataException`（ファイル名・ID・項目のパスを含む）。ゲームを始めさせない |
| 実行時の不正な操作 | 足りない素材で支払う、解放前の枠に魔晶を付ける | 例外にせず、**失敗を表す結果**（理由つき）を返す。状態は何も変えない |
| プログラムの誤り | 負の金額、null、範囲外の引数 | `ArgumentException` 系。テストで落として直す |

すべての「状態を変える操作」は、**全部成功するか、全部失敗して何も変えないか**のどちらか（02 5.6節）。

### 1.4 数と時間

- 割合は `Pct`（120 は120％）、秒は `Sec`。コードの中でも比率（1.2）に直して持ち歩かない。計算の入口で `/ 100.0` する。
- 秒は刻み（整数）に直す：`ticks = (int)Math.Round(sec * 10.0, MidpointRounding.AwayFromZero)`。変換は **1か所**（`TimeUtil.ToTicks`）に置く。
- 金額・ダメージ・HP は `double`。個数の通貨も `double` で持つが、操作は整数にして行う（5節）。
- 文字列への変換は `CultureInfo.InvariantCulture`。

### 1.5 ランクで変わる値（`Ranked<T>`）

JSON の `[a, b, c]`（★で変わる値）と数値1つ（変わらない値）を、**読み込み時に必ず3つの値に広げる**。

```csharp
public sealed class Ranked<T> { public T R0 { get; } public T R1 { get; } public T R2 { get; } public T Pick(int rank); public static Ranked<T> Of(T v); }   // rank は 0〜2。実装は S1 で済み（Assets/Game/Data/Ranked.cs）。struct ではなく不変のクラス：null（その項目が無い）を `Nullable<struct>` にせずに表せて、JSON コンバーターの扱いが単純になるため。戦闘中は使わず、`BattleSetup` を作るときに `Pick` で普通の値に直す（戦闘中に確保しない）
```

- JSON の読み込みは専用のコンバーターで、数値1つなら3つに複製、長さ3の配列ならそのまま、それ以外は `DataException`。
- tier も同じ（`"high"` か `["mid","high","supreme"]`）。null は「段階なし」。
- 値の選び方：`rank = RankFor(kind, star)`。通常スキルは `skillRankStars` が `[1,7]` なので、★0なら0、★1〜6なら1、★7以上なら2。特殊は `[3,9]`、必殺は `[5,11]`。魔晶はランクを持たない（常に0）。

### 1.6 乱数の使い方（決定性）

- 使う乱数は `Rng.Create(seed, RngStream.Battle／Gacha／Misc)` だけ。戦闘は戦闘の `Seed` から `Battle` の流れを1本作り、**戦闘の中で他の乱数を使わない**。
- 1つの判定につき、引く回数は決まっていること。確率が 0 や 100 でも `Chance` は必ず1回引く（`Rng.Chance` の仕様）。
- 引く順番を決めて守る（9.9節）。順番を変えるとゴールデンが全部変わるので、変えるときは理由を書く。

## 3. S1 Data の型と読み込み

### 3.1 型の作り方

- JSON の1ファイル＝C#の1つのルート型。**不変**（読み込んだら書き換えない）。`public IReadOnlyList<T>`、辞書は `IReadOnlyDictionary<string,T>`（列挙の順番は JSON の並びを保つため、`List` ＋ 別の索引にする。`Dictionary` の列挙順を当てにしない）。
- 列挙型（`Element`、`Role`、`CharTier`、`SkillKind`、`TriggerType`、`EffectType`、`TargetType`、`EffectWhen`、`BuffCategory`、`BuffPolarity`、`TierLevel`）は JSON の小文字の文字列と1対1。未知の値は `DataException`。
- **バフの ID は文字列のまま**（データで増える）。読み込み後に `BuffDef` への参照に解決しておく（`SkillDef` ではなく、解決済みスキル（9.1節）で整数の索引にする）。

```csharp
namespace Mado.Data {
  public sealed class GameData {                       // 全マスタのルート
    public SystemConfig System;  public IReadOnlyList<TierDef> Tiers;  public StatTables Stats;
    public IReadOnlyList<CharacterDef> Characters;  public IReadOnlyList<SkillDef> Skills;
    public IReadOnlyList<CrystalDef> Crystals;  public BuffTable Buffs;  public IReadOnlyList<CurrencyDef> Currencies;
    public TextTable Text;
    public CharacterDef Character(string id);  public SkillDef Skill(string id);  public CrystalDef Crystal(string id);  // 無ければ DataException
  }
  public sealed class SkillDef  { string Id; SkillKind Kind; TriggerDef Trigger; IReadOnlyList<EffectDef> Effects; }
  public sealed class CrystalDef: SkillDef相当 + string OwnerId; CrystalSlot Slot;   // 共通部分は SkillDefBase にまとめる
  public sealed class TriggerDef { TriggerType Type; double? EverySec, CooldownSec; double? ChancePct; double? Pct; bool Once; StatusIf If; }
  public sealed class EffectDef  {                      // 1つの型に全項目（使わない項目は null）。type ごとの意味は 9.3 節
    EffectType Type; TargetType? Target; Element? Element; Ranked<double> MultiplierPct; Ranked<double> BonusSelfLostHpPct; bool Bonus;
    string BuffId; Ranked<TierLevel?> Tier; Ranked<double> DurationSec; double? ChancePct; EffectWhen? When; StatusIf If;
    Ranked<double> Sec; double? Pct; double? Max; CountUnit? Unit; CountScope? Scope;
    int? MinRank; TriggerType? OnTrigger; Ranked<Element[]> TargetElements;     // Ranked<…> は、その項目が無いとき null
  }
}
```

- `StatusIf`：`targetHasAnyStatus` の buffId 配列。
- 追加の項目（`needsReview` など、今は無いもの）は、スキーマが `additionalProperties: false` なので、**読み込みも未知の項目を拒否する**（`MissingMemberHandling.Error`）。JSON Schema と C# の型がずれたらすぐ分かるようにするため。
- `characters.json` の `enabled`（省略時 true）は、フェーズ1で10体に絞るために使う。
- 実装（S1。**C# は未コンパイル**）のファイル：`Assets/Game/Data/` の `Enums.cs`・`EnumStringConverter.cs`・`Ranked.cs`・`SkillDefs.cs`・`BuffDefs.cs`・`CharacterDefs.cs`・`ConfigDefs.cs`・`GameData.cs`・`TextTable.cs`・`DataSources.cs`・`DataLoader.cs`・`DataValidator.cs`・`DataException.cs`・`IsExternalInit.cs`。テストは `Assets/Game/Tests/Data/`。
- **S1 で決めたこと**
  - `init` を使うのは Data だけ（`IsExternalInit` は Data の内部クラス。Core が使うと CoreLib で二重になるので、`check_sources.py` が Core の `init`・`record` を禁止している）。
  - 必須の項目：`[JsonObject(ItemRequired = Required.Always)]` をクラスに付け、省略できる項目だけ `[JsonProperty(Required = Required.Default)]`（キャラの `enabled`）や `double?`・参照型で表す。`levelTable` の最大レベルの `expToNext` は `Required.AllowNull`。`TriggerDef`・`EffectDef` は項目の大半が任意なので、`type` などだけを `Required.Always` にした。
  - 列挙型は `[JsonConverter(typeof(EnumStringConverter))]`。綴りは `[EnumMember(Value = "…")]`。DataLoader の設定にも同じコンバーターを登録してあるので、属性が効かない型（Nullable の扱いなど）でも読める。
  - コレクションは `IReadOnlyList<T>`／`IReadOnlyDictionary<string,T>`（Newtonsoft は `ReadOnlyCollection`／`ReadOnlyDictionary` にして読む）。**辞書の列挙順は当てにしない**。順番が要るものは、JSON の配列（`Tiers`、`Characters` など）を使う。
  - `onTrigger` の型は `TriggerType?`（値は `onHit`／`onCrit`）。`scope` は `target`／`enemy_all`（`CountScope`）。
  - `TriggerType` に `unknown` は無い（スキーマには残っているが、データに出たら読み込みが落ちる）。`needsReview` も型に無い（出たら落ちる）。
  - 検証の Code：`ID_DUPLICATE`・`REF_MISSING`・`SKILL_KIND_MISMATCH`・`OWNER_MISMATCH`・`TEXT_MISSING`・`SUBSTAT_STARS`・`OBTAIN_MISMATCH`・`CRYSTAL_KIND`・`EFFECT_FIELD_MISSING`・`TIER_MISSING`・`TIER_UNKNOWN`・`TIER_UNEXPECTED`・`RANK_NOT_INCREASING`・`ALWAYS_WITH_DURATION`・`MINRANK_RANGE`・`NO_DAMAGE_OR_HEAL`・`ULTIMATE_COOLDOWN`・`COUNT_TOTAL`・`COUNT_TIER`・`CRYSTAL_SLOTS`・`ELEMENT_CYCLE`・`DEVMODE_HASH`・`SYSTEM_VALUE`・`LEVEL_TABLE`・`STAR_TABLE`・`AWAKEN_SUM`・`ROLE_MULTIPLIER_MISSING`・`SKILL_RANK_STARS`・`ENEMY_SCALE`・`GROWTH_COVERAGE`。読み込み側：`FILE_MISSING`・`JSON_PARSE`・`SCHEMA_VERSION`。
  - **Unity（IL2CPP・マネージコードの削除）で動かすときは、`Assets/link.xml` で `Mado.Data` を残す**（リフレクションで読むプロパティが削られるため）。Unity のプロジェクトを作るときに足す（S9）。
  - コンパイルできない環境のため、`tools/bootstrap/check_csharp.py` が、C# のソースを読んで「Newtonsoft がこの実データを受け付けるか」を再現して確かめる（キー・必須・値の種類・列挙の綴り・Ranked の形・括弧の釣り合い）。`check.sh` に入っている。dotnet が使えるようになっても残す（型を直したときの早い関門になる）。

### 3.2 読み込み

```csharp
public interface IDataSource { string ReadText(string relativePath); }      // "characters.json" など。無ければ DataException
public static class DataLoader { public static GameData Load(IDataSource source);               // エラーがあれば DataException
                                 public static DataLoadResult LoadWithIssues(IDataSource source); } // 例外にせず、問題の一覧（警告も）と GameData（型変換に失敗したときは null）を返す
```

- 実装は3つ：`FileDataSource(rootDir)`（dotnet、Mado.Sim、テスト、Unity のエディタ）、`MemoryDataSource`（テストで壊したデータを渡す。1か所だけ差し替える `With`、全ファイルを写す `CopyOf`）、Unity の実行時に `TextAsset` から作る実装（View。S9）。
- 読み込みの手順：①全ファイルを文字列で読む → ②型に変換（未知の項目はエラー） → ③**参照の解決**（キャラ→スキル・魔晶、バフ ID、魔晶の ownerId がそのキャラの `crystalId` と相互に一致） → ④`DataValidator.Validate`。②〜④の失敗は、全部まとめて `DataException`（問題の一覧を持つ）で投げる。1つ目で止めない（実際には、ファイルごとに最初の型変換エラーで止まり、全ファイルぶんを集める。型変換に失敗したファイルが1つでもあれば、③④は走らせない）。
- `text/ja.json` は `Dictionary<string,string>`。`TextTable.Get(key)` は、キーが無ければ**キーそのものを返す**（画面に出て気づける）。

### 3.3 `DataValidator`（Core 側で使える軽い検証）

02 4.10節のうち、**JSON Schema 以外**を C# で書く。4節の Sim の validate もこれを呼ぶ。

- 参照：スキル・魔晶・バフ・通貨・アセットの ID が実在する。`ownerId` ↔ `crystalId` が対応する。
- 人数：キャラ105（SSR 103＋LR 2）、格の内訳（極17・天38・煌19・彩11・灯13・素5）。
- スキル：全キャラが3種を持つ。ランク配列の長さ。段階が要るバフ（`tiers` に `none` が無いもの）に `tier` がある。`none` のバフに `tier` が付いていない。`tier` の値がそのバフの `tiers` に存在する。
- `trigger.type: always` の効果に `durationSec` が付いていない。`minRank` は0〜2。
- 無敵を付けるだけの必殺（`damage`／`heal` が無い）は許す。
- 結果は `DataIssue { Severity, Code, Message, Path }` のリスト。Code は短い英字（`REF_MISSING`、`TIER_MISSING` など）にして、テストで Code を確かめる。

### 3.4 テスト（S1）

## 4. S2 Mado.Sim の validate

- `tools/Mado.Sim`（net8.0 のコンソール）。コマンド：`validate`／`golden`／`battle`／`economy`／`calibrate`。S2 では `validate` だけ作る。
- `validate` の中身：①各 JSON を `Schemas/*.schema.json` で検査（JSON Schema draft 2020-12 のライブラリ。NuGet の JsonSchema.Net を第一候補とし、使えなければ別のものにして理由を決定記録に書く） ②`DataLoader.Load` ＋ `DataValidator` ③警告の扱い（`--strict` で警告もエラー）。終了コードは、エラーがあれば1。
- **置き換え方**：S2 が終わるまでは `tools/bootstrap/validate.py` が正。C# 版を作ったら、同じデータと、壊したデータ（`Tests/Fixtures/bad_*.json`）の両方で **Python と C# の結果が一致する**ことを確かめてから、`scripts/check.sh` の呼び出しを C# 版に変える。`validate.py` は消さずに `tools/bootstrap/` に残す（元作品の名前の照合は、`dev/sourcemap.json` を読めるこちらに残す）。
- `check.sh` の `dotnet run --project tools/Mado.Sim -- validate` は、Sim が出来るまでは呼ばない（今のスクリプトは `[ -d tools/Mado.Sim ]` で守ってある）。

## 5. S3 Wallet と開発者モード

仕様は 02 3.4節が正。ここでは型と手順を決める。

### 5.1 型

```csharp
namespace Mado.Core.Wallet {
  public readonly struct Money { public readonly string CurrencyId; public readonly double Amount; }
  public sealed class Cost   { public IReadOnlyList<Money> Items; }      // 作るときに負・NaN・無限大・重複しない形に整える
  public sealed class Reward { public IReadOnlyList<Money> Items; }
  public readonly struct PayReason { public readonly string Key; }       // "gacha.pull"、"growth.levelup" など。定数は WalletReasons に置く
  public readonly struct GrantReason { public readonly string Key; }
  public readonly struct PayResult { public bool Success; public string ShortCurrencyId; public double ShortBy; }  // 失敗のとき、足りない通貨（最初の1つ）
  public enum WalletEventKind { Spent, Granted }
  public readonly struct WalletEvent { public WalletEventKind Kind; public string CurrencyId; public double Amount; public string ReasonKey; public double BalanceAfter; }
  public sealed class WalletState { public Dictionary<string,double> Balances; public Dictionary<string,double> Carry; }  // セーブ用。順番は通貨マスタの並びで書き出す

  public sealed class Wallet {
    public Wallet(IReadOnlyList<CurrencyDef> currencies, WalletState state, Func<bool> isDevMode);
    public double Balance(string currencyId);
    public PayResult Pay(Cost cost, PayReason reason);
    public void Grant(Reward reward, GrantReason reason);
    public IReadOnlyList<WalletEvent> DrainEvents();       // セッションが取り出して、Core 内の購読者 → View の順に流す（02 3.2節）
  }
}
```

- 残高は `Wallet` の private な配列（通貨マスタの並び）。外から書き換えられる公開メンバを作らない（`WalletState` はセーブとの受け渡し用で、`Wallet` の生成時にコピーして取り込む。以後は共有しない）。
- 通貨 ID がマスタに無いときは `ArgumentException`（プログラムの誤り）。

### 5.2 Pay の手順

1. 各項目を検査：負・NaN・無限大は `ArgumentException`。同じ通貨が複数あれば合算する。金額0の項目は無視。
2. 個数の通貨（`currencies.json` の `integer: true`）は、**切り上げて整数にする**（支払い不足にならないよう、少なく見積もらない）\[仮\]。
3. 開発者モードなら、残高を変えずに成功を返す。ただし通常と同じ `Spent` イベントを出す（`BalanceAfter` は変わっていない値）。
4. すべての通貨で `残高 >= 金額` か確かめる。足りない通貨があれば、通貨マスタの並びで**最初の1つ**を `ShortCurrencyId` に入れて失敗を返す。残高・イベントは何も変えない。
5. 全部足りていれば、全部減らして `Spent` イベント（通貨ごとに1つ）を積む。

### 5.3 Grant の手順

- 検査は Pay と同じ。個数の通貨は**切り捨てて整数にし、端数は `Carry` に足す**。`Carry` が1以上になったら、その整数分を残高に足す \[仮\]（確率ドロップの繰り越し。02 3.4節）。`integer: false` の通貨は小数のまま足す。
- 開発者モードでも `Grant` は通常どおり増やす（「素材が減らない」だけの機能で、増えるのは止めない）。
- `Granted` イベントを通貨ごとに1つ。

### 5.4 開発者モード

```csharp
public static class DevMode { public static bool TryEnable(string code, string expectedSha256Hex); }   // 戻り値は一致したか。フラグは呼び出し側が SaveData に書く
```

- `code` の前後の空白を除き（`Trim()`）、UTF-8 の SHA-256 を小文字の16進にして、`system.json` の `devModeCodeSha256` と**文字列として**比べる（コードは大文字小文字を区別する：「A」と「a」は別）。比較は定数時間でなくてよい（個人用）。
- ハッシュ計算は `System.Security.Cryptography.SHA256`（netstandard2.1 にある）。
- 開発者モードのフラグは `SaveData.DevMode`。Wallet は `Func<bool>` で毎回読む（途中で切り替えても反映される）。

### 5.5 テスト（S3。02 6.3・6.7節の再掲を含む）

- Pay：足りなければ失敗、残高・イベントが変わらない／全部足りれば全部減る／複数通貨で1つだけ足りないとき何も減らない／同じ通貨の項目が合算される。
- 負・NaN・無限大は `ArgumentException`。金額0は無視。
- 個数の通貨の丸め：支払い 2.1 → 3 枚、付与 2.7 → 2 枚（`Carry` 0.7）、続けて付与 0.4 → 繰り越し 1.1 で +1 枚（`Carry` 0.1）。
- プロパティテスト：`Rng` のシード付きで、Pay／Grant／失敗する Pay のランダムな操作列を1万本。①開発者モードでないとき残高が負にならない ②失敗した Pay で何も変わらない ③残高の変化量 ＝ イベントの合計 ④決定性（同じシードで同じ最終状態）。
- 開発者モード：`TryEnable("A", ハッシュ)` が true、`"a"` と `" A "` の扱い（前者 false、後者 true）。有効のとき Pay が残高を変えず `Spent` を出す。1万回の「ガチャ相当」の Pay でも残高が不変。無効に戻すと通常の動作。
- アーキテクチャ：`Wallet` の公開メンバに、残高の辞書・配列を返すものが無い（リフレクションで公開メンバを列挙して確かめる）。`Mado.Core.Battle` が `Mado.Core.Wallet` を参照していない（`check_sources.py` が既に検査）。

## 6. S4 セーブ

### 6.1 型と流れ

形は 02 4.9節。実装で決めること：

```csharp
namespace Mado.Core.Save {
  public sealed class SaveData {
    public string Format = "madoclone-save";  public int SaveVersion;  public bool DevMode;  public string SavedAtUtc;
    public RngState Rng;  public WalletState Wallet;
    public Dictionary<string, CharacterState> Characters;             // キーはキャラID。JSON の出力順は ID の昇順に固定
    public string Leader;  public Dictionary<string, PartyState> Parties;
    public Dictionary<string, double> Metrics;  public ProgressState Progress;  public SettingsState Settings;
    public Dictionary<string, JToken> Orphans;                        // マスタに無いIDの中身。捨てずに持ち越す
    // 育成系・ガチャ・実績・放置は、フェーズが来たときに足す（キーの追加は互換、意味の変更は SaveVersion を上げる）
  }
  public sealed class CharacterState { public int Star, Lv; public double Exp; public int Copies; public string[] Crystals;  /* 長さ5。無い枠は null */ }

```

- 読み込みの流れ：`bytes` → UTF-8 → `JObject` → `format` と `saveVersion` を確認 → `SaveMigrator.Migrate`（古い版を最新に）→ `SaveData` に変換 → `SaveValidator.Validate(save, GameData)`。
- **失敗は `LoadResult`（成功／失敗＋理由）で返す**。壊れたセーブで例外を投げて落とさない。失敗したら、View 側が直前のバックアップを試す（バックアップの管理は `ISaveStore` の実装側）。
- `SaveMigrator`：`Func<JObject,JObject>` を版ごとに登録して、`v → v+1` を順に適用。**移行の前に、元の JSON を必ず取っておく**（失敗しても戻れる）。
- マスタに無いIDは読み飛ばし、警告のイベントを出し、`Orphans` に残す。次の保存でも出力する（データを戻せば復活する）。
- エクスポート：`MADOSAVE1:` ＋ base64(gzip(UTF-8 JSON))。インポートは、形式・版・スキーマ相当（`SaveValidator`）を通ってから受け入れる。`DevMode: true` のセーブは、エクスポート名に `-dev` を付ける。
- 乱数の状態：`Rng` は内部状態（uint 4つ）を取り出す／戻す手段を持つ。`RngState` は ガチャ用・その他用の4つずつを持つ。**`Rng` に `GetState()`／`FromState()` を足す**（S4 で。テストは「状態を取って戻すと同じ列が続く」）。

### 6.2 `SaveValidator`（セーブが満たすべきこと）

- 魔晶の不変条件（7.3節）：どの魔晶 ID も、全キャラを通して**高々1回**。魔晶の ID はすべてマスタにある。
- 魔晶は、**その持ち主の★が6以上のときだけ**、どこかに存在する。★6以上の持ち主の魔晶は、**ちょうど1か所**にある。
- 枠 `i` に魔晶があるなら、そのキャラの ★ が `crystalSlotStars[i]` 以上。
- 編成のスロットに入っているキャラは所持している。リーダーは所持キャラで、★5以上（`leaderMinStar`）\[リーダー神殿の解放条件。フェーズ2で確認\]。
- Lv は `1〜starMaxLv[star]`。★は0〜11。

違反は `SaveIssue` のリストにして、「直せるもの」（枠の解放前に付いた魔晶を外す、など）は自動で直さず、**警告として返して読み込みを失敗にしない**\[仮：個人用で、壊れたセーブでも遊べるほうが良い。ただし不変条件は `Repair` で直した結果を返す\]。

### 6.3 テスト（S4）

- 往復：`SaveData` → JSON → `SaveData` が等しい。桁の大きい `double`（1e15 超）が数値のまま往復する。
- キーの出力順が固定（同じ状態を2回書き出して、バイト列が一致）。
- 移行：`Tests/Fixtures/save_v1.json`（最初の版）を読める。将来の版が増えるたび、古いフィクスチャを残す。
- 壊れた入力：空、途中で切れた JSON、`format` が違う、`saveVersion` が新しすぎる → `LoadResult` の失敗（例外にならない）。
- 孤児：マスタに無いキャラ ID を含むセーブを読む → 読めて、保存し直しても残る。
- 魔晶の不変条件違反（同じ魔晶が2か所、★不足の枠）を `SaveValidator` が検出する。
- エクスポート／インポートの往復。`MADOSAVE1:` が先頭。別の接頭辞は失敗。
- 乱数の状態を保存して戻すと、続きの列が一致する。

## 7. S5 所持キャラと魔晶の移動

### 7.1 責務

- `RosterService`：所持キャラの追加（フェーズ1ではデバッグの付与。ガチャは後）、★・Lv の変更。★が変わったら `CrystalService.OnStarChanged` を呼ぶ。
- `CrystalService`：魔晶の置き場所の管理と、移動。**費用はかからない**。Wallet を使わない。

### 7.2 型

```csharp
namespace Mado.Core.Growth {
  public readonly struct CrystalPlace { public readonly string CharacterId; public readonly int Slot; }       // Slot は 0〜4
  public enum MoveFailure { None, UnknownCrystal, CrystalNotObtained, UnknownCharacter, CharacterNotOwned, SlotOutOfRange, SlotLocked, SamePlace }
  public readonly struct MoveResult { public bool Success; public MoveFailure Failure; public string SwappedCrystalId; }   // 入れ替わった魔晶（無ければ null）
  public readonly struct CrystalMoved { public string CrystalId; public CrystalPlace From, To; public string SwappedCrystalId; }  // イベント

  public sealed class CrystalService {
    public CrystalService(GameData data, SaveData save);                      // save.Characters の Crystals を直接の状態として使う
    public bool TryFind(string crystalId, out CrystalPlace place);
    public IReadOnlyList<string> Equipped(string characterId);                // 長さ5。無い枠は null（解放前の枠も null）
    public bool IsSlotUnlocked(string characterId, int slot);                 // star >= system.crystalSlotStars[slot]
    public MoveResult Move(string crystalId, string toCharacterId, int toSlot);
    public void OnStarChanged(string characterId, int oldStar, int newStar);  // 6を跨いだとき、固有魔晶を ★6 の枠（index 2）に置く
    public IReadOnlyList<CrystalMoved> DrainEvents();
  }
}
```

### 7.3 手順と不変条件

**Move(crystalId, toCharacterId, toSlot)**（どれか1つでも該当すれば、その理由で失敗し、何も変えない。上から順に判定）：

1. 魔晶 ID がマスタに無い → `UnknownCrystal`
2. どのキャラの枠にも無い（持ち主が6凸未満） → `CrystalNotObtained`
3. 移動先のキャラがマスタに無い → `UnknownCharacter`／セーブに無い（未所持） → `CharacterNotOwned`
4. `toSlot` が0〜4の外 → `SlotOutOfRange`
5. 移動先の枠が解放前（移動先のキャラの★が `crystalSlotStars[toSlot]` 未満） → `SlotLocked`
6. 移動元と移動先が同じ → `SamePlace`

成功：移動先が**空**なら、移動して元の枠を空にする。移動先に**別の魔晶がある**なら、2つを入れ替える（その魔晶は移動元の枠に入る。移動元の枠は解放済みのはずなので、入れ替えが失敗することはない）。同じキャラの中の入れ替え（枠の並べ替え）も同じ手順。`CrystalMoved` を1つ積む。

**OnStarChanged**：`oldStar < 6 <= newStar` のとき、そのキャラの固有魔晶（`characters.json` の `crystalId`）を、`crystalSlotStars` で `6` に当たる枠（index 2）に置く。**その枠は、★6になった瞬間に開いたばかりなので必ず空**（空でなければプログラムの誤りとして `InvalidOperationException`）。★は下がらないので、魔晶が消える経路は無い。

**不変条件**（テストで常に確かめる）：
- (a) 同じ魔晶 ID が2か所に現れない。
- (b) 持ち主の★が6以上なら、その魔晶は**ちょうど1か所**にある。★6未満なら、**どこにも無い**。
- (c) 枠 `i` に魔晶があるなら、そのキャラの★は `crystalSlotStars[i]` 以上。
- (d) 失敗した `Move` は、状態もイベントも変えない。
- (e) どのキャラの枠にも、どの魔晶でも入る（枠の種類の制限は無い。ユーザー確認済み）。`crystals.json` の `slot`（normal／rainbow）は見た目の区別だけ。

**戦闘との関係**：魔晶の効果の `self`・`target`・`attacker` は、**付けているキャラ**から見た相手を指す（持ち主ではない）。戦闘用の `BattleSetup` を作るとき、キャラの `Equipped` を**枠の順に**読んで、各魔晶を「付けているキャラの追加スキル」として解決済みスキルにして渡す。魔晶の `ownerId` は戦闘に渡さない。

### 7.4 テスト（S5）

- 6凸になった瞬間に、持ち主の枠 index 2 に固有魔晶が入る。5凸以下では入らない。
- 持ち主以外へ移せる：A の固有魔晶（枠2）を、B（★6以上）の空の枠へ。A の枠が空になり、B に入る。
- 入れ替え：A の魔晶と、B の枠にある魔晶を交換。2つとも動く。同じキャラ内の枠の入れ替えも。
- 失敗：未知の魔晶／6凸前の魔晶（まだ存在しない）／未所持のキャラ／枠が範囲外／解放前の枠／同じ枠。失敗の後でセーブ全体が変わっていない（ディープコピーとの比較）。
- 解放前の枠への移動（★3のキャラの枠3）は `SlotLocked`。★8になれば成功。
- 固有魔晶を他のキャラに渡したあと、持ち主の枠2は空いていて、別の魔晶を入れられる。
- ランダムな操作列（Move／★アップ）を1万本流して、不変条件 (a)〜(d) が常に成り立つ（`Rng` のシード付き）。
- イベント：成功した `Move` で `CrystalMoved` が1つ。入れ替えなら `SwappedCrystalId` が入る。

## 8. S6 ステータスの算出

### 8.1 型

```csharp
namespace Mado.Core.Stats {
  public struct BattleStats {            // 戦闘に渡す、解決済みの実数
    public double Atk, Hp, Def;
    public double EvasionPct, AccuracyPct, CritRatePct, CritResistPct, CritDamagePct, CritDefensePct;
    public double AttackSpeed;           // 1.0 から始まる倍率（02 2.4節）
    public double Power => Hp + 3.0 * (Atk + Def);
  }
  public enum StatKey { Atk, Hp, Def, Evasion, Accuracy, CritRate, CritResist, CritDamage, CritDefense, AttackSpeed }
  public enum ModifierPool { Global, DragonNest, LeaderLv, Flat }    // 割合の3つの輪（01 6.4節）と、％ポイントや実数の足し算
  public readonly struct Modifier { public StatKey Stat; public ModifierPool Pool; public double Value; }   // Value は Pct。Flat は ％ポイント（または AttackSpeed の％）
  public interface IModifierSource { void Collect(ModifierSink sink, in StatQuery query); }
  public readonly struct StatQuery { public string CharacterId; public int Star, Lv; public Element Element; public bool IsLeader; }
  public sealed class StatResolver { public BattleStats Resolve(CharacterDef c, CharacterState s, bool isLeader); }
}
```

### 8.2 式（01 の2.0・4.6・6.4節が正）

```text
基礎        = levelTable[Lv] × roleMultipliers[role] × starMultipliers[★] × tiers[格].statMultiplier      （Atk・Hp・Def のそれぞれ）
最終 Atk    = 基礎 Atk × (1 + ΣGlobal/100) × (1 + ΣDragonNest/100) × (1 + ΣLeaderLv/100)     ※ LeaderLv はリーダー本人にだけ。Hp・Def も同様
副ステータス = system.baseSubstats + ΣFlat（アカウント共通の出どころ）+ キャラ個別の加算（substatBonuses の★以下の分 ＋ 竜の巣の属性別 ＋ リーダー神殿）
攻撃スピード = 1 + ΣFlat(AttackSpeed)/100、上限 system.attackSpeedMax
```

- Lv は `1〜starMaxLv[★]` に収める（範囲外は呼び出し側のバグ。`ArgumentException`）。表は Lv 1〜120。
- `levelTable` の値は**全体強化が乗る前の基礎値**（Lv1＝攻撃225・HP8,500・防御60。`docs/decisions/2026-11-15_取り込みと基礎マスタ.md`）。仕様書4.6節の実測値（Lv1でHP 15,671k）は全体強化が乗った後なので、そのまま基礎にすると二重になる。
- **フェーズ1〜2は全体強化の出どころ（広場・研究・コレクションなど）がまだ無い**。基礎値のままでは、難易度（ランク1の推奨戦力が45M）に対して戦力が約9千で、4桁以上足りない。そこで、**`ProfileModifierSource`（`IModifierSource` の1つ）が、ランクごとの「標準的な育ち具合」の共通倍率を `Global` の輪に足す**（定義は10節の `sim_profiles.json`）。フェーズ3以降に本物の出どころ（広場など）が入ったら、`ProfileModifierSource` は戦闘シミュレーション専用にして、ゲーム本体では使わない（ゲーム本体の切り替えは `GameSession` の設定。S9）。
- `substatBonuses`（凸ボーナス）は、キャラ個別の加算として足す（出どころが何であれ StatResolver は変えない）。
- 魔晶は副ステータスを足さない（効果はスキルとして戦闘で働く）。
- `Resolve` は**純粋関数**（同じ入力で同じ出力）。乱数・時刻を使わない。

### 8.3 テスト（S6）

- 表引き：★0・Lv1 の遠距離キャラが Atk 225／Hp 8500／Def 60（`stat_tables.json` の測定値）。近距離は roleMultipliers を掛けた値。LR は ×1.1。
- ★とLv：★ごとの `starMultipliers`、Lv の上限（★0 で Lv51 は例外）。
- 副ステータス：基礎値＋凸ボーナス（★2・4・8・10 を越えた分だけ加算。★3 なら★2の分だけ）。
- プールの合成：Global と DragonNest が**掛け算**で合成される。LeaderLv はリーダー本人にだけ効く（同じ入力で `isLeader` が違うと結果が違う）。
- 戦力：`Hp + 3×(Atk+Def)`。★0・Lv1の遠距離キャラ（基礎値のみ）は 8,500 ＋ 3×(225＋60) ＝ **9,355**。`ProfileModifierSource` で倍率を掛けると、その倍率ぶん（攻撃・HP・防御それぞれ）大きくなる。
- `ProfileModifierSource`：ランクごとの共通倍率が `Global` の輪に入り、`LeaderLv` や `DragonNest` には入らない。倍率 0 のとき（出どころ無し）は基礎値のまま。

## 9. S7 戦闘

最も大きい。**式は 01 の2.1・2.2節、流れは 02 5.1〜5.3節が正**。ここでは、型、効果の評価、乱数を引く順番など、**そこに書かれていない部分を決める**。

### 9.1 型

```csharp
namespace Mado.Core.Battle {
  public enum Side { Ally, Enemy }
  public enum Row { Front, Mid, Back }
  // ----- 入力（JSON にそのまま書き出せる。解決済み。ID ではなく中身） -----
```

- `SkillResolver.Resolve(SkillDef, rank, GameData) → ResolvedSkill`：ランクの選択（1.5節）、`minRank` を満たさない効果の除外、秒→刻み、バフ ID→索引、`if` のバフ ID 配列→ビットマスク（状態の種類は 32 以下）、`targetElements`→属性のビットマスクにする。**ここまでが Core の育成側の仕事。BattleSim は ID も JSON も知らない**。
- 戦闘の中のユニットは、事前に確保した配列で持つ（`BattleUnit` クラスを最大 7＋敵の数だけ作る。1刻みごとに `new` しない）。状態異常・バフは固定長の配列（1体あたり最大24個。超えたら古い順に捨てず、`Aux` つきのイベントで警告して付与を無視 \[仮\]）。
- `Row` は味方・敵とも `UnitSetup` で受ける。味方の既定の割り当ては `FormationRules`（Core.Growth、フェーズ1で作る）が role から決める \[仮：近距離・防御→前列、回復→中列、遠距離・妨害→後列。01 3.1節の「前列（タンク・近距離）、中列（サポート・回復）、後列（遠距離・妨害）」に合わせた〕。

### 9.2 1刻みの流れ（02 5.1節の詳細）

```text
Start():
  tick = 0。各ユニット：HP = Stats.Hp、必殺のクールタイム = CooldownTicks（満タンから数える [仮]）、
    interval の残り = EveryTicks（最初の発動は N 秒後 [仮]）、攻撃の進行度 = 0、onHpBelow は未発動
  onBattleStart の効果を、固定順（味方スロット順 → リーダー → 敵）で発動。続けて always の効果を期限なしで付ける
Step():
  1. tick += 1。tick が制限時間以上なら、敗北で終了（時間切れ）
  2. 全ユニットの状態を更新：期限切れの状態を外す（付与からの経過で判定）、継続ダメージ・継続回復の時刻に来たものを処理
  3. 味方の順（スロット順 → リーダー）→ 敵の順に、生きているユニットを処理：
       行動不能（cannotAct：氷結・束縛）→ このユニットの攻撃・interval・必殺ゲージの進行をすべて飛ばす
       通常スキル：進行度 += AttackSpeed × tickSec ÷ baseAttackIntervalSec。1以上の間、攻撃して 1 引く（1刻みに複数回ありうる）
       特殊スキル：interval なら残りを減らし、0 なら発動して EveryTicks に戻す
       必殺スキル：残りを 1 減らす（沈黙＝ultimateGaugeStopped の間は減らさない）。0以下なら発動して CooldownTicks に戻す
       魔晶：interval のものは特殊スキルと同じ
     （HP が 0 になったユニットは、その刻みの残りの行動をしない）
  4. サポート（使い魔・契約霊・竜。フェーズ3で追加。今は何もしない）
  5. イベントのキューを、連鎖の上限（chainLimit=64）まで処理する（9.7節）
  6. 勝敗：敵全滅→勝利／味方（編成6体＋リーダー）全滅→敗北。相打ちの刻みは味方の勝ち \[仮：02 5.1節\]
```

- 戦闘の最大長は `timeLimitSec`（ステージ60秒・ボス60秒・最終ボス180秒・試練30秒など）。刻みに直して `BattleRules.TimeLimitTicks`。
- スキップ（開始1秒後から）は View の話。Core は `RunToEnd` で最後まで進めて結果を返すだけ。

### 9.3 スキルの実行（効果の評価）

1つのスキルの発動を `SkillRunner.Run(unit, skill, context)` とする。`context` は、発動のきっかけの情報（きっかけの相手：`target`／`attacker`）。

**準備**（効果を1つも実行する前に1回だけ）：
1. **対象の選び方の決定**：効果が `enemy_*` を使うなら、`primary`（主対象の敵1体）を**1回だけ**選ぶ（9.6節。乱数を引くのはここ）。以後、同じスキルの `enemy_single`＝`[primary]`、`enemy_area`＝`primary` と同じ列の生きている敵、`enemy_all`＝生きている敵全員（添字の昇順）。`target`＝ きっかけの敵（`onHit`・`onCrit` なら当たった相手、無ければ `primary` の集合）。`attacker`＝ `onDamaged` で攻撃してきた相手。
2. **状態のスナップショット**：全ユニットの「いま付いている状態の種類のビットマスク」を記録する。`if` の判定は**このスナップショット**で行う（そのスキルで付けた状態は数えない。02 4.3節の約束）。デバフの数（`debuffCountBonus`）も同じスナップショットで数える。
3. **補正の計算**：`elementCountBonus` と `debuffCountBonus` を、スキルの中のほかの効果に適用する補正に直す。
   - `elementCountBonus`（`pct`）＝ `min(max, 出場中の生きている味方で element が一致する人数 × CountPerUnit)` を、同じスキルの **`damage` と `heal` の倍率に足す**。
   - `elementCountBonus`（`sec`）＝ 同じ式で、同じスキルの **`applyBuff` の効果時間（秒）に足す**。
   - `debuffCountBonus`（`scope: target`）＝ **敵1体ごとに**、その敵に付いているデバフ・状態異常の数 × `pct` を、その敵に当たる `damage` の倍率に足す（`max` で頭打ち）。`enemy_all` なら敵全員の合計を数える。
   - 「出場中の味方」には**自分を含める**。**生きているユニットだけ**数える \[仮：戦闘不能のユニットは出場していないとみなす\]。
4. **主ヒットの結果の記録領域**を空にする（`hit[target]`、`crit[target]`、`anyHit`、`anyCrit`）。

**実行**（`Effects` の並びの順に）：

| effect | 手順 |
|---|---|
| `damage` | 対象ごと（添字の昇順）に、ダメージ計算（9.4節）。`if` が付いていて、その対象のスナップショットが条件を満たさなければ、その対象はスキップ。`bonus: true` は**直前の（`bonus` でない）ダメージと同じ命中・クリティカルの結果を使う**（乱数を引き直さない）\[仮\]。結果を `hit[target]`・`crit[target]` に記録 |
| `heal` | 対象の味方ごとに、`発動者の有効 Atk × (MultiplierPct + 補正) / 100`。治癒禁止（`healBlocked`）の対象には 0。回復量は最大 HP を超えない。`chancePct` があれば 9.3.1 |
| `applyBuff` | 対象ごとに、`when`・`if`・`chancePct` を満たしたものに付与（9.5節）。`when: afterHit` は、**対象が敵ならその敵に命中したとき、味方・自分なら（スキル全体で）1体でも命中したとき**に満たす。`when: onCrit` も同様にクリティカルで。`onTrigger` は、親の trigger とは別のきっかけ（通常スキルの命中／クリティカル）で付与する効果（9.7節） |
| `gaugeShift` | 対象の必殺ゲージを `ShiftTicks` だけ動かす（正で進める＝残りを減らす、負で戻す＝残りを増やす。クールタイムの上限で止める）。沈黙中も動かせる。`when`・`if`・`chancePct` は `applyBuff` と同じ |
| `cleanse` | 対象の味方の、デバフ・状態異常・拘束（`polarity: debuff`）をすべて外す |
| `dispel` | 対象の敵の、強化（`polarity: buff`）をすべて外す（`invincible` などの `none` 段階のものも含む） |
| `reflect` | 今のデータには無い。実装しない（検証で `reflect` が出たら警告） |
| `elementCountBonus`／`debuffCountBonus` | 準備で処理済み。実行では何もしない |

#### 9.3.1 確率（`chancePct`）の判定

- 発動の確率（`trigger.chancePct`）は、きっかけごとに1回引く（9.7節）。効果の `chancePct` は**別の判定**。
- 効果の `chancePct` は、**対象ごとに**引く。「X％で味方ごとに」＝ `ally_all` ＋ `chancePct: X` ＝ 味方1人ずつが X％（02 4.3節）。
- **連続して並んでいて、同じ対象・同じ確率の効果は、1つの判定を共有する**（例：`005_u` の「50％で攻撃アップとシールド」は、味方ごとに1回引いて両方付ける）。共有の単位は「`Effects` の並びで隣り合い、`Target` と `ChancePct` と `When` が同じ `applyBuff`／`heal`／`gaugeShift`」。
- **前提（`when`・`if`・`minRank` を満たす）が成り立たない効果では、乱数を引かない**。

### 9.4 ダメージ計算（`DamageCalc`。純粋関数）

01 の2.1・2.2節の式を、**ここ1か所**に書く。入力は攻撃側・防御側の**スナップショット**（有効 Atk／Def、命中率、回避率、クリティカル率・耐性・ダメージ・防御、属性）と、倍率、乱数。

```text
1. 無敵（damageImmune）の対象 → ダメージ 0。イベントは出す（Immune）。以降の乱数は引かない
2. 命中：bonus でない主ヒットだけ判定する。chance = clamp(攻撃側の命中率 − 防御側の回避率, hitChanceMinPct, hitChanceMaxPct)
         rng.Chance(chance) が false なら外れ（Miss イベント）。bonus は主ヒットの結果をそのまま使う
3. クリティカル：発生率 = clamp(クリティカル率 − 相手のクリティカル耐性, 0, 100)。命中したときだけ rng.Chance を引く
         （クリティカルシールド critDamageImmune の対象なら、クリティカルは発生しない＝通常ダメージ [仮]。このときも乱数は引く）
         クリ倍率 = max(critMultiplierMin, (クリティカルダメージ − 相手のクリティカル防御) ÷ 100)。クリティカルでなければ 1.0
4. 基礎 = 攻撃力 × (倍率 + 補正) / 100 ×（1 + 攻撃の増減の合計）、さらに bonusSelfLostHpPct があれば 基礎 += (自分の最大HP − 現在HP) × pct / 100 [仮：基礎に加える]
         攻撃の増減の合計は、有効 Atk の計算に含める（9.5節）。0 未満は 0
5. 防御 = 防御力 ×（1 + 防御の増減の合計）、0 未満は 0
6. ダメージ = max(minDamage, (基礎 − 防御) × 属性倍率 × クリ倍率)
7. ダメージ反射（reflectPct を持つ対象）：受けたダメージの reflectPct % を、攻撃者に反射する（反射は防御・属性・クリティカルを無視。反射したダメージはさらに反射されない）[仮]
8. シールド：対象の shield の残りから先に減らし、残りを HP から引く。HP が 0 以下になったら戦闘不能（9.7節の onDeath・onKill）
```

- `defenseBuffAppliesBeforeSubtract`（system.json）は、今 `true`（防御バフを引く前に適用）。`false` のときの挙動は、01 の第11章の計測結果が出てから書く（今は `true` 固定で、スイッチは作らず、項目の存在だけ検査する）。
- 命中で `Chance` を引く回数は、**対象ごとに1回（bonus を除く）**。クリティカルも対象ごとに1回。順番は「命中→クリティカル」を対象の添字の昇順で繰り返す。
- DOT（継続ダメージ）は `DamageCalc` を通さない。9.5節。

### 9.5 バフ・状態異常

**状態インスタンス**：`{ BuffIndex, Tier, CasterId, CasterAtkAtApply, ExpireTick, NextTickAt, ShieldRemaining }`。`always` の効果は `ExpireTick = int.MaxValue`（期限なし）で、**発動者が戦闘不能になった刻みに外す**（02 4.4節）。

**付与**（`Apply(target, buff, tier, durationTicks, caster)`）：
1. **無効化**：対象が `cc_barrier`（`immuneTo: [bind, freeze]`）を持ち、付与するのが束縛・氷結なら、付与しない（イベントも出さない）。対象が `invincible` でも、デバフは付けられる（無敵はダメージだけを防ぐ）\[仮\]。
2. **重ね掛け**（buffs.json の `stackRule`）：同じ ID が既にあるとき、`sameTier: replace`（新しい方で上書き：残り時間・発動者・記録した攻撃力を更新）、`lowerTier: ignore`（低い段階を後から付けても何も変えない。効果時間も延ばさない）、`keepHigherTier`（高い段階を後から付けたら置き換える）。**違う ID は加算**（別のインスタンス）。段階なしのバフ（`none`）は常に `replace`。
3. 容量（24）を超えるなら付与しない（警告のイベント）。

**有効ステータス**（`Effective(unit)`）：基礎の `BattleStats` に、付いている状態の `statMods` を合成する。**1刻みごとに全部を再計算せず、状態が変わったときにだけ**再計算する（ダーティフラグ）。
- `op: pct`（Atk・Def・クリティカルダメージ・クリティカル防御）：`最終 = 基礎 × max(0, 1 + Σ value/100)`（同じステータスの増減を合計してから1回掛ける）。
- `op: pt`（クリティカル率・クリティカル耐性・命中率・回避率）：`最終 = 基礎 + Σ value`（％ポイントを足す）。
- 火傷の `atk -30%`、痺れの `def -30%`、氷結の `crit_def -50%`、暗闇の `accuracy -10pt` も、同じ合成に入る。

**毎秒の処理**（付与から 10 刻みごと。`NextTickAt`）：
- `dotAtkPct`（火傷・痺れ・出血）：`CasterAtkAtApply × dotAtkPct / 100` のダメージ。**防御・属性・クリティカルの影響を受けない**\[仮\]。シールドで吸収される。無敵の対象には入らない。
- `hotAtkPct`（持続回復・天竜の加護）：`CasterAtkAtApply × hotAtkPct / 100` を回復（治癒禁止中は 0）。
- 継続ダメージで HP が 0 になれば、倒した相手は付与した発動者（`onKill` の対象にする）。

**そのほかの挙動**：
- シールド：付与時に `ShieldRemaining = 対象の最大HP × shieldMaxHpPct / 100`。期限切れで消える。シールドの buffId は `shield` の1つだけなので、同時に複数あることはない（重ね掛けの規則で1つに決まる）。
- `taunt`（`forceTargetCaster`）：付けられたユニットは、**付けた相手（`CasterId`）が生きている間、その相手を狙う**（9.6節）。
- `heal_block`：回復の量が 0（回復イベントは出さない）。`silence`：必殺ゲージの減少が止まる。
- `crit_shield`：受けるクリティカルが通常ダメージになる \[仮\]。`reflect_shield`（30％）：受けたダメージの30％を攻撃者に返す \[仮\]。`cc_barrier`：束縛・氷結を無効。`invincible`：ダメージを受けない。
- **段階の指定**：`tier` がランク配列なら、解決時に選んである（`ResolvedEffect.Tier`）。段階なしのバフの効果に `tier` は付かない。

### 9.6 狙いの選び方（02 5.3節の詳細）

- **敵（相手側）の主対象**：生きているユニットのうち、**前列→中列→後列の順で、最初の空でない列**から1体。その列に複数いれば `rng.NextInt(n)` で選ぶ（添字の昇順に並べた n 体から）。**挑発（`taunt`）のかかっているユニットが攻撃するときは、挑発した相手が生きていればその相手を主対象にする（乱数を引かない）**。
- `enemy_area`：主対象と**同じ列**の、生きている敵全員。
- `ally_lowest_hp`：生きている味方のうち「現在HP ÷ 最大HP」が最小の1体。**同率は、編成スロット順（リーダーは最後）で先の方**。
- `ally_element`：生きている味方のうち `element` が一致する全員（スロット順）。`ally_all`：生きている味方全員（スロット順、リーダーが最後）。`self`：発動者。
- **「自分」「味方」「敵」は発動者から見た側**で決める（敵ユニットにとっての「味方」は敵側）。

### 9.7 トリガーとイベントのキュー

| trigger | きっかけ | 確率 | 備考 |
|---|---|---|---|
| `attackInterval` | 通常スキル（攻撃の進行度が1に達した） | ― | |
| `interval` | `everySec` ごと | ― | 最初の発動は N 秒後 \[仮\] |
| `cooldown` | 必殺ゲージが0に | ― | 発動後に `cooldownSec` に戻す |
| `onHit` | **自分の通常スキルの攻撃が命中した** | `chancePct` | `if`（`targetHasAnyStatus`）があれば、**命中した相手が条件を満たす**ときだけ |
| `onCrit` | 自分の通常スキルがクリティカルになった | なし（必ず） | |
| `onDamaged` | 自分が攻撃（ダメージ）を受けた | `chancePct` | `attacker` は攻撃してきた相手 |
| `onBattleStart` | 戦闘開始（tick 0） | ― | |
| `onDeath` | 自分が戦闘不能になった | ― | |
| `onKill` | 自分が相手を倒した | ― | |
| `onHpBelow` | 自分の HP の割合が `pct` 以下になった | ― | `once: true` なら一度だけ |
| `always` | 戦闘開始から、フィールドにいる間 | ― | 効果は期限なしのバフ。発動者が戦闘不能で外れる |

- 発動の確率は**きっかけごとに1回**（`Chance` を引く。確率が100でも引く）。
- `onHit`／`onCrit` は、**通常スキルの攻撃が1回当たるごとに**、そのユニットの特殊スキルと魔晶の中から該当するものを**キューに積む**。同じ刻みの中でキューを順に処理して発動する。
- **同じ刻みに重なったときの順番**（02 4.3節）：通常 → 特殊 → 必殺 → 魔晶（枠の順）。同じ種類は、ユニットの処理順（スロット順 → リーダー → 敵）。
- キューの処理の回数は `chainLimit`（64）を上限にし、超えたら**残りを捨てて、警告イベント（`ChainLimit`）を1つ出す**。
- `onTrigger`（効果の項目）：親のスキルの trigger（たとえば特殊スキルが `onCrit` のとき）とは別に、**通常スキルの命中時／クリティカル時**にも判定して付与する効果（例：3凸から「通常命中後10％で束縛を追加」）。親のスキルが発動したかに関係なく、きっかけで判定する。
- `onDeath`：戦闘不能になった刻みのキューに積む。そのユニットは死んでいるが、**この発動だけは実行する**（`self` は死んだ本人）。`always` の効果は同じ刻みで外れる。

### 9.8 イベント

`BattleEventType`：`Damage`、`Miss`、`Immune`、`Heal`、`Shield`、`BuffApplied`、`BuffRemoved`、`SkillFired`、`GaugeShifted`、`Death`、`Warning`（`ChainLimit`、`StatusCapacity`）、`BattleEnd`。

- `Source`・`Target` はユニットの添字（味方 0〜、敵はその後）。`Value` は数値（ダメージ・回復量）、`Aux` は補助（バフの索引、スキルの種類、クリティカルなら 1 など）。
- **イベントは事前に確保したバッファに struct で書く**（1刻みごとに確保しない。1戦闘の上限は 200,000 件 \[仮\] で、超えたら `Warning`）。
- `BattleResult.EventHash`：イベントの列を SHA-256 にして、先頭 8 バイトを `ulong` にしたもの。**エンコード**：1イベントにつき `Tick`（int32、リトルエンディアン）、`Type`（1バイト）、`Source`・`Target`（int16）、`Value`（`double` のビット列を int64 で）、`Aux`（int32）。

### 9.9 乱数を引く順番（決定性の決まり）

戦闘の乱数は `Rng.Create(setup.Seed, RngStream.Battle)` の1本だけ。引く順番を固定する。

1. 刻みの中のユニットの処理順（9.2節）。
2. 1つのスキルの中では、**準備で主対象を選ぶ**（必要なら1回）→ 効果を並びの順に → 1つの効果の中では対象を添字の昇順に。
3. `damage` の1対象：命中 → （命中したら）クリティカル。
4. `applyBuff`／`heal`／`gaugeShift` の `chancePct`：共有グループごと、対象の添字の昇順に1回。前提が成り立たなければ引かない。
5. トリガーの確率：きっかけの発生順（キューに積んだ順）に、処理するときに引く。

### 9.10 テスト（S7）

**DamageCalc（手計算の10ケース以上）**：
- 基本（攻撃100・倍率100・防御0 → 100）、属性有利×1.2・不利×0.8、命中の下限5％（回避が高すぎる）・上限100％、クリ倍率の下限1.0（クリティカル防御が高すぎる）、最低1ダメージ（防御が上回る）、攻撃力ダウンの重ね掛けで基礎が0以下→1ダメージ、`bonusSelfLostHpPct`、`debuffCountBonus` と `elementCountBonus` の補正（人数 0・1・上限超え）、無敵の対象、クリティカルシールド。
- 乱数は固定値を返すモック（`IChanceSource` 的な抽象を `DamageCalc` の引数にして、本番は `Rng`）で、命中・外れ・クリティカルを選べる。

**状態・バフ**：期限切れ、`sameTier: replace`・`lowerTier: ignore`・`keepHigherTier`、違う ID は加算、継続ダメージ（付与時の攻撃力を使う。発動者の攻撃力が後で変わっても不変）、沈黙中は必殺ゲージが進まない、氷結・束縛で行動が飛ぶ、治癒禁止中は回復0、`cc_barrier` が束縛・氷結を防ぐ、`taunt` で狙いが固定、`always` の効果が発動者の戦闘不能で外れる、シールドが先に減る、容量オーバーで警告。

**トリガー・効果の評価**：
- `if.targetHasAnyStatus`（or）：範囲スキルで、条件を満たす敵だけに入る。同じスキルで付けた状態は数えない（スナップショット）。
- `bonus`（追加ダメージ）が、主ヒットの命中・クリティカルをそのまま使う。
- `elementCountBonus` の `pct`／`sec`、`debuffCountBonus`（敵ごとに別の値）。
- `chancePct`：対象ごとに引く／連続した同じ確率の効果が判定を共有する／前提が成り立たないと乱数を引かない。
- `minRank`（解決時に除外される）、`onTrigger`、`targetElements`（ランクごとの属性）。
- `onHit`／`onCrit`／`onDamaged`／`onDeath`／`onKill`／`onHpBelow(once)`／`onBattleStart`／`interval`／`cooldown`、重なったときの順番、連鎖の上限。
- `gaugeShift` の進める・戻す、クールタイムの上限。

**決定性**：同じ `BattleSetup` を2回走らせて `EventHash` が一致。シードが違えば（ほぼ確実に）違う。`RunToEnd` と、`Step` を回し続けたときの結果が一致。ゴールデンは10節。

**アーキテクチャ**：`Mado.Core.Battle` が Growth・Progress・Economy・Wallet・Session・Save を参照していない（`check_sources.py`）。`BattleSim` の `Step` の中で `new` していない（ベンチマークで割り当てバイト数を測る：`GC.GetAllocatedBytesForCurrentThread` で、ウォームアップ後の1,000刻みが 0 バイト）。

## 10. S8 ゴールデンと戦闘シミュレーション

- **ゴールデン**（02 6.4節）：`Assets/Game/Tests/Core/Golden/setup_*.json` に、**解決済みの `BattleSetup`**（ステータスの実数・スキルの中身・バフの写しを含む）を10種類置く。近接中心／遠距離中心／回復あり／妨害あり／LR入り／ボス戦／制限時間切れ／状態異常が多い／魔晶つき／デバフ数・属性人数の補正あり。`golden_expected.json` に、それぞれの `EventHash`・勝敗・終了刻みを置く。
- ゴールデンを作る手順：`Mado.Sim golden --update` が `setup_*.json` を読んで期待値を書き出す。**更新のコミットには変えた理由を書く**。
- 同じテストを、Unity EditMode と dotnet test の両方で走らせてハッシュが一致することを確かめる（Unity が使えるようになってから）。
- **スナップショット**（代表10戦の勝敗・決着時間・総ダメージの上3桁）は、マスタから組み立てた戦闘で別に持つ。データを変えたら変わってよく、差分を人が読む。
- `Mado.Sim battle`：`--setup file.json --n 1000 --seed0 1`。`seed0 + i` で1,000戦し、勝率・決着時間の分布・総ダメージを表示する。1,000戦が1分以内（02 5.5節）。出力は `out/`（コミットしない）。
- マスタから `BattleSetup` を作る部分（`BattleSetupBuilder`）は、S8 の後半。育成状態（`CharacterState`）＋ `StatResolver` ＋ `SkillResolver` ＋ `FormationRules` で味方を作り、`StageFactory`（フェーズ1の後半）で敵を作る。
- **`sim_profiles.json`（ランクごとの「標準的な育ち具合」。02 6.5節が前提にしているが、これまで定義が無かった。ここで定義する \[仮\]）**：
  ```json
  { "schemaVersion": 1, "items": [ { "rank": 1, "star": 0, "lv": 50, "partyCharacterIds": ["chr_101", "..."], "globalMultiplier": { "atk": 0, "hp": 0, "def": 0 } } ] }
  ```
  `star`・`lv` は 01 の6.1節の表の「想定 ★／Lv」。`partyCharacterIds` は、そのランクで普通に組める7体。**`globalMultiplier` は、`Mado.Sim` が計算して書き込む**（手で書かない）：標準編成7体の戦力が、そのランクのボスの推奨戦力（`difficulty.json` の式）と**ちょうど等しくなる**共通倍率（攻撃・HP・防御は同じ倍率の1つの値から始め、各ステータスの比は基礎値のままにする）。そのうえで `calibrate` が `enemyScale` を動かして、勝率を合格ラインに合わせる。
  - `Schemas/sim_profiles.schema.json` を足し、`validate` は（空でも）通す。
  - この方法なら、全体強化の中身（広場・研究など）が無くても、フェーズ1の戦闘のバランスが取れる。01 6.4節の「各ランクで必要な全体倍率（ランク15で約5千倍…）」は、ここで出る値と**あとで突き合わせて確かめる**（大きくずれたら、`difficulty.json` の `e1` か、基礎値の見方を見直す）。

## 11. S9 GameSession の最小形（Unity が要る）
