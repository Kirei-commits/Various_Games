# 05 コーディング指針（リファクタリングで得たこと）

作成：2026-11-16。S2〜S8 と calibrate を作ったあと、品質を固めるリファクタリングをした（記録：`docs/decisions/2026-11-16_リファクタリングとテストの強化.md`）。そのとき**何を見て、何を直したか**を、次にコードを書くときの指針に直したもの。コードを書く前に読む。守れなかったら、理由を `docs/decisions/` に残す。

## 1. 進め方（手順）

1. **直す前に、安全網を作る**。リファクタリングは「挙動を変えない」ことが条件なので、変えていない証拠が先に要る。使った証拠は3つ：①ゴールデンのハッシュ（`golden`）②calibrate の結果の一致 ③ランダムな戦闘の不変条件テスト。
2. **カバレッジで「テストが無い所」を探す**（`scripts/coverage.sh --lines 名前`）。通っていない行・片側しか通っていない分岐は、**仕様が未検証の所**。実際、ここからバグが2つ出た（4節）。
3. **テストが本当に効くかは、本体をわざと壊して確かめる**（生存チェックを外す、など）。壊しても緑のテストは、守っていない。
4. **バグを見つけたら、先に再現するテストを書く**（CLAUDE.md）。直したあとも、テストは残す。
5. **1つの整理 = 1つのコミット的なまとまり**で、整理のたびに `dotnet test` を流す。ゴールデンが動いたら、整理ではなく挙動の変更なので、理由を書いて `golden --update`。
6. 終わりに `scripts/check.sh` と `scripts/coverage.sh` を通し、`docs/decisions/` に記録し、CLAUDE.md の進捗欄を更新する。

## 2. 何を「直すべき」と見るか（観点）

| 観点 | 目安 | 直し方（今回の例） |
| --- | --- | --- |
| **長い関数** | 1つの関数に「準備→実行」のような段階が複数ある | 段階ごとに名前のある関数へ（`RunSkill` → `NeedsPrimary`／`SnapshotStatuses`／`ComputeCountBonuses`／`ResetHitRecord`）。名前が、そのまま仕様の見出しになるように |
| **同じ形のループ・処理の重複** | 3回目が出たらまとめる | トリガーを積む3つのループ → `EnqueueTriggers`。標準編成を組む処理（calibrate・テスト・ゴールデンに別々）→ `ProfilePartyFactory` |
| **同じ型の引数が並ぶ** | `double` が4つ以上並ぶ。取り違えても型で気づけない | 名前付きの入力の型にする（`DamageCalc.Damage` の10個 → `DamageInput`）。テストのヘルパーは引数の順をコメントに書く |
| **魔法の数・文字列** | 意味のある数字や文字列がコードに直書き | 定数に（`OwnCrystalSlot`、敵の種類の文字列）。ゲームの数値は定数ではなく **Data（JSON）**（不変条件2）。calibrate の標準値も JSON（`allySubstats`） |
| **static の可変状態** | ツールでも避ける（並列で呼べなくなる） | クラスにして状態をインスタンスに（`Calibrator`） |
| **探し方・道具の重複** | テストごとに実データの探し方がある | 共有の道具に（`TestData`）。使われていないコードは消す |
| **読みにくい数式** | 浮動小数の誤差の対処が、本文に混ざる | 小さな関数に名前を付けて、理由を書く（`Wallet.TakeWhole`、攻撃の進行度の `ProgressEpsilon`） |
| **依存の向き** | 名前空間が逆向きに参照している | `check_sources.py` に規則を足す（Battle は Save を参照しない、Wallet・Save は戦闘・育成を参照しない） |

**やりすぎない**：生存チェックのような「安全側の重複」は、1つ外してもテストが落ちなくても、残してよい（理由を決定記録に書く）。抽象を増やすのは、重複が3回出てから。

## 3. 書くときの約束（コードの規約）

- **Core・Data は netstandard2.1・C# 9**。`init`・`record` は Data だけ（Core では使わない）。`UnityEngine`・`System.Random`・`DateTime.Now`・戦闘ループ内の `Math.Pow` は使わない（`check_sources.py` が検査する）。
- **失敗の扱いは3種類を混ぜない**（docs/04 1.3節）：データの誤り＝`DataException`（読み込み時）／実行時の不正な操作＝失敗を表す結果（例外にしない。状態は何も変えない）／プログラムの誤り＝`ArgumentException` 系。
- **状態を変える操作は、全部成功か、全部失敗して何も変えないか**。失敗するかもしれない確認は、状態を変える前に済ませる（`RosterService.TrySetStar` は魔晶側を先に呼ぶ）。
- **戦闘の `Step` の中で `new` しない**（配列は構築時に確保。テストで 1000 刻み 0 バイトを確認している）。LINQ・`foreach` のボックス化・文字列連結を `Step` に入れない。
- **乱数は `Rng` だけ。引く順番は仕様**（docs/04 9.9節）。順番を変えるとゴールデンが全部変わる。確率が 0・100 でも引くものと、引かないもの（効果の `chancePct` ≥ 100、前提が成り立たない効果）を区別する。
- **`Ranked<T>` はマスタを読むためだけ**。戦闘用のデータ（`BattleSetup`）には入れず、`SkillResolver` が `Pick(rank)` で普通の値にして渡す（書き出すと読み戻せない形になる）。
- **ID・文字列で書く所は定数か列挙型にする**。画面の文言・名前は `text/ja.json`。元作品の名前・画像・文章は入れない。
- **コメントは日本語で、「なぜ」を書く**。何をしているかは名前で分かるように。`[仮]` の挙動を実装したら、docs/04 の12節の表に1行足す。
- **名前**：テストは「何が、どうなる」（`Shield_AbsorbsDamageBeforeHp`）。`Resolve`・`Build`・`TryXxx`（失敗を返す）の使い分けを守る。

## 4. テストの書き方（観点）

- **表で書く**：検査が並ぶものは、1行1検査の表にする（`DataValidatorCodeTests`）。そして**表が漏れていないことをテストにする**（`DataValidator.cs` の Code を正規表現で拾い、表に無いものがあれば落ちる）。検査を足して表を忘れると気づける。
- **ランダムな網を持つ**：個別のテストで書ききれない組み合わせ（スキル×バフ×トリガー）は、実データからランダムに組んで、**どの戦闘でも成り立つこと**を見る（`BattleInvariantTests`）：HP の範囲、生死とイベントの一致、与ダメージの合計、勝敗と生存の一致、警告が出ないこと、決定性。網が片寄っていないこと（勝ちも負けも出る）も確かめる。
- **失敗した操作は何も変えない**を、状態の前後比較（シリアライズして文字列を比べる）で確かめる。
- **境目を書く**：0・1・上限・上限+1、空、null、範囲外。小さな部品でも、誤った使い方（`ArgumentNullException` など）をテストにする。
- **モック**：確率は `IChanceSource`（`ScriptedChance`）で「命中する／しない」を選び、引いた回数と確率の値も確かめる。時刻は `IClock`（予定）。
- **データ駆動のバランスは、回帰テストで守る**：`CalibrationTests`（標準編成の戦力＝推奨、ランク1・8・16・32 のボス勝率が 65〜95％）。落ちたら `calibrate --write` で合わせ直す。
- **dotnet だけで動かすテスト**（開発ツールの部品。`tests/Sim`）と、Unity の EditMode でも動かすテスト（`Assets/Game/Tests`）を分ける。後者は NUnit だけに依存する。

## 5. 変更の種類ごとの「やること」

| 変えるもの | 必ずやること |
| --- | --- |
| 戦闘のルール・スキル・バフのデータ・難易度 | ①`golden` が動くか見て、意図した変更なら `golden --update` と理由 ②`calibrate --write`（`CalibrationTests` が落ちる）③docs/04 12節 |
| マスタ JSON | `validate`（C#・Python）、`check_csharp.py`、必要なら `DataValidator` の検査と `DataValidatorCodeTests` の表 |
| セーブの形 | `SaveMigrator` に移行を足し、**古い版のフィクスチャを残す**（`Tests/Fixtures/save_v*.json`）。意味を変えたら `LatestVersion` を上げる |
| 素材の増減 | 必ず `Wallet.Pay`／`Grant`（不変条件3）。開発者モードのテストを足す |
| 新しい育成要素 | `IModifierSource` を実装する（StatResolver を変えない）。`SaveData` にキーを足す（互換）。`MetricCounter`（予定）に数えさせる |

## 6. 今回のリファクタリングで見つけたもの（再発を防ぐための記録）

1. **イベントの上限で警告が出ていなかった**：上限の処理が「黙って捨てる」になっていた。仕様に「警告を出す」と書いてあっても、**上限に達するテストが無い**と気づかない。→ 上限・容量・連鎖の限界には、**必ず「達したとき」のテスト**を書く。
2. **戦闘不能のユニットにバフが付きうる経路**（死亡時発動のスキルが `self` に付与）：いまのデータには該当が無かったので、**データが増えてから**壊れるところだった。→ 「今のデータでは起きない」ことに頼らない。安全側に倒して、テストで固定する。
3. **生存チェックが3層にあり、1つ外してもテストが落ちない**：安全側の重複として残したが、「どれか1つで足りる」ことを知っておく。
4. **calibrate の探索が逆向きに進む不具合**（勝てないときの決着時間を 0 にしていた）：探索の目的関数は、**「欠測」を有利な値で表さない**（無限大にする）。
5. **ランダムな網は、本体の壊し方を教えてくれた**：わざと壊したとき、個別のテストではなく不変条件テストとゴールデンが落ちた。個別のテストを増やすより、網を持つほうが効く場面がある。
