# CLAUDE.md — GOD ARENA（神器大戦）

ゴッドフィールド風の属性バトル。**ビルド不要・実行時依存ゼロ**の単体Webアプリ。
`index.html` をブラウザで開けばそのまま動く。

## 構成

```
index.html          マークアップ。<script> の並び順が依存関係そのもの
css/style.css       テーマ・レイアウト・アニメーション
js/items.js         アイテム定義と抽選（純データ。他に依存しない）。`isShield()` が守りに使える種類の判定
js/engine.js        ルールと進行（純ロジック。items に依存）。`resolveDamage` が計算の核
js/ai.js            AI（期待ダメージの見積もり + 相手の防具読み）。items/engine に依存
js/storage.js       localStorage 永続化
js/audio.js         Web Audio API による効果音の合成
js/render.js        DOM 描画。items/engine/ai に依存
js/main.js          進行役とUIバインド。上記すべてに依存
tests/              テスト
```

## 開発コマンド

```bash
npm ci && npm test   # lint → ロジック → E2E
npm start            # http://127.0.0.1:8081/
```

CI はリポジトリ直下の `.github/workflows/ci.yml`（god-arena と gomoku-narabe の両方を回す）。
**サブディレクトリ配下の `.github/workflows/` は GitHub では実行されない**。

## 壊してはいけない設計上の制約

1. **実行時の依存パッケージをゼロに保つ。** ビルド工程を持ち込まない。
   Playwright は開発時のみの依存で、配信物には含めない。
2. **ESモジュールを使わない。** `file://` で直接開いた時に CORS で失敗するため、
   各ファイルは即時関数で `window.GA` 名前空間に公開するクラシックスクリプトにする。
   したがって **`index.html` の script の順序が依存関係**（`npm run lint` が検査する）。
3. **`localStorage` は必ず try/catch で包む。** 読み書きの両方が例外を投げうる。
4. **乱数を直接呼ばない。** `Engine.setRandom()` / `AI.setRandom()` を通す。
   テストと `?seed=` による再現のため。
5. **設定キーは必ず `Store.DEFAULTS.settings` に定義する。** 定義漏れのキーは
   `merge()` で捨てられ、保存しても復元されない。
6. **ルール判断は engine に集約する。** UI と AI は同じ関数（`availableActions` /
   `canPray` / `resolveDamage`）を見る。UI側で条件を書き直すと必ずずれる。
7. **一画面に収める。スクロールしてよいのは手札だけ。**
   `body` は `100dvh` の縦並び、`.arena-area` はグリッドで手札の行だけが
   `minmax(0, 1fr)`。`.layout` と `.arena-area` の `min-height: 0` を外すと
   子のスクロールが効かなくなる。狭い画面では戦況ログを引き出し（`#side.is-open`）に
   逃がして場所を取らない。`tests/e2e/layout.spec.mjs` が
   「ページが縦にスクロールしないこと」「44×44px 以上」を検査している。
8. **`[hidden] { display: none !important; }` を消さない。**
   `.abtn { display: flex }` が既定の `[hidden]` に勝ってしまい、
   隠したはずの防御ボタンが出たままになる（実際にこれで落とした）。
9. **アイテムの種類で分岐するときは `Items.isShield()` を使う。**
   `kind === 'defense'` と直接書くと、反射具（`kind: 'reflect'`）が漏れる。
   実際に main.js の4箇所で漏らし、反射具を防御に出せない状態で落とした。
10. **`Engine.defend()` を呼ぶ前に攻守のIDを控える。**
   呼んだ後は `pending` が消え、決着ならログ末尾に `over` が積まれる。
   ログ末尾から `actor` を取る書き方は壊れる。
11. **ふうじ（封じ）の検査は `attack` / `defend` / `useItem` の3箇所すべてに要る。**
   最初に `defend` と `useItem` だけに入れて `attack` を忘れ、
   封じられた武器で攻撃できる状態で落とした。手札から何かを出す口が増えたら、
   そこにも `isSealed()` の検査が必要か必ず確かめる。
12. **防御の数値は `Engine.previewDefense()` を通す。**
   `resolveDamage()` を直接呼ぶと、のろいによる減衰（`defenseScale`）と
   神の加護が抜ける。UIのプレビューとAIの判断と実際の解決が、必ず同じ数字に
   なるようにここを通す。**加護は「通ったダメージ」と「撃ち返し」の両方にかかる**
   （撃ち返しは攻撃側の加護を見る。片方だけ入れてプレビューと実際がずれた）。
13. **攻撃側のAIの見積もりにも加護を掛ける。** `Engine.graceScale(target)` を
   忘れると、瀕死の相手を「倒せる」と誤認して手札を使い切る。
14. **手札のカード（`<button>`）は flex コンテナにしておく。**
   button は中身のブロック要素から高さが決まらず、説明の行が黙って切れる
   （実測で `scrollHeight 81 / clientHeight 69` を確認）。`display: flex` に
   すると中身の高さがそのまま効く。`layout.spec.mjs` の
   「手札のカードの中身が切れない」が回帰を見張っている。
15. **攻撃の結果は属性ごとの内訳で見せる（`Render.breakdown`）。**
   「何ダメージ」だけでは、どの属性が防げてどれが通ったのか読めない
   （遊んだ人からの指摘）。受ける前のプレビューと解決後の結果で同じ関数を使う。
   - **行の合計は必ず実ダメージと一致させる。** 加護で減らすときは
     `Engine.applyGraceToResult()` が `rescaleRows()` で内訳も比例配分する。
     片方だけ減らすと「行の合計 ≠ 合計」になって信用されない。
   - **`res.blocked` には撃ち返した分が含まれる。** 「防いだ」として出すときは
     `blocked - reflected` にする（二重に数えてしまう）。
   - 帯の長さは `blocked + through` の最大値で揃える。`raw` で揃えると
     会心（1.5倍）の行が基準を超える。
16. **画面操作の乱数はゲームの乱数と分ける（`uiRandom`）。**
   狙い先の抽選に `Engine.random()` を使うと、押すたびに引きとAIの判断が
   ずれて `?seed=` の再現性が壊れる。
17. **演出の待ちは取りこぼされることがある。**
   通しプレイで、仕掛けた `setTimeout` と `requestAnimationFrame` の両方が
   発火しない場面を捕まえた（ページは生きていて、先に仕掛けた別の
   `setInterval` は回り続けていた）。そのため
   - `wait()` はタイマーと描画フレームの両方で締め切りを見る
   - 5秒動かなければ見張り番（`startWatchdog`）が復帰させる
   - 復帰時に**世代番号 `game.gen` を上げる**。古い処理は `stale()` で降りる
   **`newGame()` でも世代を上げる。** 上げないと、前の対局で待っていた処理が
   目を覚まして新しい局面を触る（rAF は止められない）。

## ダメージ計算の形（resolveDamage）

攻撃は **命中パケット** に展開してから防具を割り当てる。

1. `toPackets()` … 連撃(hits)は回数分のパケットに分かれる。それ以外は
   同じ性質（属性・貫通・会心）どうしをまとめる（防具を重ねて受けられるため）。
2. 防具の割り当て … **反射具を先に**、次に強い防具から順に、いちばん多く止められる
   パケットへ充てる。同じだけ止まるなら**連撃の1回分**を選ぶ（残りの防具を
   重ねる余地を残せるので、防御側に有利）。
3. 会心の判定 … パケットの被ブロックが **0 のときだけ** 1.5倍。
   1点でも防がれたら乗らない。

**この順序を変えるとルールが変わる。** 反射を後回しにすると撃ち返せる量が減り、
連撃を優先しないと防具が無駄になる。どちらも「出した側が損しない」ための順序。

## ゲーム設計上、動かすと壊れるもの

- **武器を持っている間は祈れない**（`Engine.canPray`）。
  これを外すと、全員が「祈って引き直す」を選び続けて試合が終わらなくなる。
  実際に4人戦が600手で未決着になり、この制約を入れて解消した。
- **手札上限で祈ったとき、引いた分を捨ててはいけない。**
  価値の低い手札の方を捨てる（`Engine.give`）。逆にすると、防具と食料で手札が埋まった
  プレイヤーに永久に攻め手が来なくなる。
- **AIは相手の手札を見ない。** 見えているのは `state.log` に残った「何で防いだか」だけ。
  `AI.readDefenses()` はログからしか読まない。ここで手札を覗くと難易度が壊れる。
  相手カードの「厚／薄」の帯は、この関数の結果をそのまま人間にも見せたもの。
  **AIだけが持つ情報を作らない**ためにこうしている。
- **反射具に `all` 属性を付けない。** どの属性でも撃ち返せると「受け一択」になり、
  攻める判断が消える。`tests/lint.mjs` が検査している。
- **同属性に反射具と防具が重なったら、反射具を先に充てる。**
  撃ち返せる量が最大になる（出した側に有利な）配分にしている。逆にすると
  反射具を出す意味が薄れる。
- **撃ち返しは防げない。** 攻撃側が防具を持っていても通る。
  これが「大技を1属性に寄せない」理由になっている。
- **ふうじの対象は engine が相手の手札から決める（`strongestElement`）。**
  かける側に選ばせない。「必ず痛いところに当たるが、狙って当てられない」ことが、
  攻撃側に相手の手札を推測させる圧力になっている。
- **状態異常の重ねがけでターン数を伸ばさない。** 残りの長い方を採る
  （`applyHex`）。伸ばせるようにすると毒だけで押し切れてしまう。
- **多人数戦は集中砲火で壊れる。** 「武器を持っていたら必ず攻撃」なので、人数分の
  火力が毎ラウンド誰か1人に集まる。対策を入れる前は 4人・6人戦とも
  「最初の脱落者が動けた手番数」が中央 **1手**、6人戦では4人に1人が
  **一度も行動しないまま**消えていた。効いた対策は3つで、どれも外すと戻る。
  1. **神の加護**（残りHP4割以下で被ダメージ半減。どくには効かない）
  2. **人数に応じたHP**（`HP_PER_EXTRA_PLAYER`）
  3. **AIが集中砲火を避ける**（`targetValue` の `PILE_AVOIDANCE`。
     瀕死を優先しない。とどめの動機は lethal ボーナスが持っている）
  `tests/logic/fairness.test.mjs` が回帰を見張っている。
- **集中砲火の回避はラウンド単位で数えない。** `AI.damageThisRound()` は
  **直近ひと回り分の移動窓**で数える。ラウンド単位だと、ラウンドの先頭で全員ぶんが
  一斉に忘れられるため手番順に偏りが出る（4人戦で最後の手番の勝率が
  **36.2%**／期待25%まで偏っていた。移動窓にして 24〜26% に収まった）。
- **1対1だけ、後手に神器を1つ渡す**（`DUEL_SECOND_BONUS`）。先手が1回多く攻撃
  できるぶん有利で、実測 54.7%（1200局 ±2.8pt）だった。3人以上では手番順の偏りが
  逆向き（後ろが有利）になり、同じ補正を足すと3人戦で 41.6% まで悪化したので当てない。
- **加護で減った分を「防いだ」に数えない。** `applyGraceToResult()` は
  `blocked` を書き換えず、行ごとの `graced` に分けて持つ。書き換えると
  防具を出していないのに防いだことになり、同じ点を二重に数える。
- **「素通りした」の判定に `through` と `raw` を比べない。** 加護で `through` が
  減ると、防具を持っていないのに止めたように見えて `AI.readDefenses` が誤読する。
  実際に止まったか（`blocked`）だけを見る。
- **難易度のパラメータは測って決める。** `AI.LEVELS` の値は当て推量ではなく、
  撹拌シードで各400局を回して選んでいる。いじったら必ず測り直す。
- **1局が短くなると腕の差が消える。** 特性つき武器を入れた直後、手数の中央値が
  29→18手に縮み、ゴッド vs かけだしが 71%→60% まで落ちた。
  HPを40→48に上げて手数を戻すと、勝率も戻った（71.7%）。
  **アイテムを追加したら必ず手数の中央値も測る。** 勝率だけ見ていると原因を見失う。
- **特性つきの武器は素の武器より火力を低くする。** 同火力だと特性が純粋な上乗せに
  なり、アイテムプール全体が強くなって上の問題が起きる。火力と当たり方は引き換え。
- **`power` は連撃1回分の火力。** カードには `4×2` のように出す。
  合計火力で書くと計算式と食い違う。

## テストの構成

| 種別 | 場所 | 実行 | 内容 |
| --- | --- | --- | --- |
| 静的検査 | `tests/lint.mjs` | 依存不要 | 全JSの構文、参照の実在、読み込み順、アイテム定義の整合 |
| ロジック | `tests/logic/*.test.mjs` | `node --test` | ダメージ計算、進行、AIの妥当性、難易度の序列、永続化 |
| ブラウザ | `tests/e2e/*.spec.mjs` | Playwright | 攻撃・防御・祈り・設定・レイアウト |
| 通しプレイ | `tests/playtest.mjs` | `npm run playtest` | 実ブラウザで決着まで遊び、詰み・停止・表示崩れ・JSエラーを探す |
| 画面の確認 | `tests/shots.mjs` | `npm run shots` | 主要画面を撮って、一画面に収まっているかを機械と目の両方で確かめる |

### 通しプレイ（playtest）について

E2Eは「決めた局面が期待通りか」を見る。通しプレイは「**最後まで遊べるか**」を見る。
人の手番の判断はページ内の `AI.chooseAction` にさせるので、まともな進行になる。

これで実際に見つけた問題:
- 同じ相手をもう一度タップすると攻撃ではなく選択解除になっていた（2連続で同じ相手を狙えない）
- 多人数戦で自分が何もできずに退場していた（下の「集中砲火」参照）
- 表示用ログを300件で打ち切っていたため、進行の判定に `log.length` が使えなかった
  （`state.events` を足した。**進行しているかの判定に `log.length` を使わない**）

**ブラウザを取得できない環境では `PW_CHROMIUM` に実行ファイルのパスを渡す。**
Playwright を上げると配置済みのブラウザではリビジョンが合わなくなるが、
この環境では取得が拒否されるため `npx playwright install` は使えない。
`playwright.config.mjs` と `tests/playtest.mjs` が `PW_CHROMIUM` を見て起動する。
CIは自分でブラウザを入れるので、この変数は未設定のままでよい。

E2Eは `desktop`（マウス）と `mobile`（Pixel 5 / `hasTouch`）の2プロジェクトで走る。
端末差のある操作は `tests/e2e/fixtures.mjs` の `tap()` に閉じ込め、スペック本体に分岐を書かない。

### バランスを測るテストの決まり

- 難易度の序列は **各300局・先後入れ替え** で測る。40局では運で逆転して
  フレーキーになる（実際に 23/39 で落ちた）。
- **シードは `mixSeed()` で撹拌してから使う。** `seed = i * 31 + 7` のような
  等差の並びは mulberry32 の内部加算と噛み合って乱数列どうしが相関し、
  **同じ実装なのに系列によって勝率が 61% と 73% に分かれた**。
  等差シードの120局で測った「77%」を一度そのまま報告してしまっている。
- 閾値は実測の95%信頼区間の下限より、さらに下に置く（実測71% → 閾値62%）。
- 勝率の数値だけでなく**序列そのもの**も assert する
  （数値が通っても順番が崩れることがある）。
- `seededRandom` でシードを固定する。フレーキーなテストは無いテストより悪い。

## 過去の失敗と、繰り返さないためのルール

- **テスト結果は `0 failed` を明示的に確認する。** passed の件数だけを見て判断しない。
- **手で確認したことはテストとして残す。** 「一度動いた」より「壊れたら気づける」を優先する。
- **外部の識別子（Actionsのバージョン等）は記憶で書かない。**
  `git ls-remote --tags https://github.com/actions/checkout` のように実際に確かめる。
